Система обработки ошибок: от «400 с SQL-запросом» к единому формату

В auth-api уже 11 роутеров, база, Redis, RabbitMQ, Celery, вход через Яндекс и Telegram-бот. А вот ошибки обрабатываются в каждом роутере по-своему, и некоторые из них прямо опасны. Сегодня сначала проводим аудит: ломаем свой API и смотрим, что видит клиент. Потом строим систему из четырёх частей: свои исключения, обработчики с единым форматом, middleware с request_id и правила для ошибок чужих сервисов.

ЧТО ПОЯВИТСЯ В AUTH-API

  • app/core/errors.py — иерархия исключений: NotFoundError, ConflictError, ExternalServiceTimeout… Сервисы бросают их и ничего не знают про HTTP-ответы.
  • app/core/error_handlers.py — один формат для всех ошибок, включая 404 несуществующего маршрута, 422 валидации и 500: Problem Details (RFC 9457) с code и request_id.
  • app/core/request_context.py — middleware: заголовок X-Request-ID, строка доступа на каждый запрос и [request_id] в каждой строке лога.
  • Клиент GitHub, который переводит ошибки чужого сервиса в наши: лимит GitHub больше не превращается в «403 у вас нет прав».
  • Регистрация без SQL в ответе, с защитой от гонки и с честным 201, когда RabbitMQ лежит.
  • 8 тестов без Redis, RabbitMQ и интернета.

АНАЛОГИЯ: ОКОШКО В БАНКЕ

«Вы не заполнили поле „паспорт“» — 4xx: клиент может исправить сам. «У нас упала программа, приходите позже» — 5xx. Плохой операционист на ваш вопрос показывает экран с красной ошибкой и номером строки кода. Хороший говорит «технический сбой, номер обращения 4471», а сам пересылает скриншот в IT. Номер обращения — это наш будущий request_id.

Ломаем свой API

Запустите auth-api (Redis и RabbitMQ работают) и пройдите по сценариям — это и есть аудит.

Третий ответ стоит разобрать на занятии вслух. Клиент получил: имя СУБД, таблицу, все колонки, SQL-запрос и хеш пароля. Источник — две строки в auth.py:

except Exception + str(e) = «покажи клиенту всё, что угодно, что пошло не так». Сервис проверяет только имя, email не проверяет — и до клиента долетает IntegrityError из SQLAlchemy со всеми потрохами. А четвёртый ответ (422) вернул обратно присланный пароль "input":"123": если ответы логирует прокси или фронтенд, пароли окажутся в логах.

Первый ответ: «ошибка в вашем запросе» (400) с адресом объекта в памяти. Клиент честно повторяет — а Борис, оказывается, уже зарегистрирован: брокер упал после записи в базу. И ни одной строки в логах от нашего кода — только шум переподключения aio_pika.

403 для нашего клиента значит «у вас нет прав». Фронтенд покажет «доступ запрещён» или разлогинит пользователя. А на самом деле это наш сервер исчерпал лимит у GitHub. Код чужого сервиса нельзя просто переслать: status_code=e.response.status_code в github.py и weather.py — та же ошибка. Плюс в тексте — внутренности чужого ответа, включая IP нашего сервера.

Здесь всё «правильно» — 500 без деталей. Но это текст, а не JSON: фронтенд, который делает await r.json(), упадёт второй раз уже у себя. И по жалобе «у меня ошибка в 14:32» строку в логе не найти: в ней нет ни пути, ни пользователя, ни идентификатора.

02 · Свои исключения

live-coding~15 мин

Почему не HTTPException везде? Потому что register_user вызывается не только из роутера: его может вызвать Celery-задача, бот или скрипт seed.py. «HTTP 409» для них бессмысленно. Сервис должен сказать что случилось («такой пользователь уже есть»), а как это показать клиенту — дело слоя API.

Сервис: проверяем и имя, и email

Было raise ValueError('Username already exists') — ValueError бросает пол-Python, и except ValueError в роутере поймал бы что угодно. Своё исключение ловится только там, где его ждут.

Два запроса с одним email пришли одновременно. Оба проверили «email занят?» — оба получили «нет», оба делают INSERT. Один победит, второй упадёт на UNIQUE в базе — тем самым IntegrityError. Последнее слово всегда за ограничением в базе, поэтому ловим его там, где делаем commit:

Три из пяти запросов прошли проверку в сервисе, и только UNIQUE в базе их остановил. Без try/except в репозитории эти три получили бы 500.

except Exception — ТОЛЬКО ТАМ, ГДЕ ВЫ ЗНАЕТЕ, ЧТО ДЕЛАТЬ ДАЛЬШЕ

Широкий except Exception оправдан в двух местах: в последнем обработчике (блок 03) и там, где ошибку осознанно гасим и логируем (блок 06). Во всех остальных случаях он прячет баги: KeyError из-за опечатки превратится в «400 Bad Request», и вы будете месяц искать, почему у пользователей «неверный запрос».

03 · Обработчики и единый формат

live-coding~15 мин

Фронтенду нужен один формат ошибки, чтобы написать один обработчик в fetch-обёртке. Придумывать свой не будем: есть стандарт RFC 9457 «Problem Details for HTTP APIs». Поля type, title, status, detail, instance — из стандарта, а code и request_id — наши расширения, стандарт это разрешает. Бонус: detail остаётся строкой, как у HTTPException, — старый фронтенд, который читает err.detail, не сломается.

04 · Middleware и request_id

live-coding~15 мин

Пользователь пишет в поддержку: «в 14:32 вылезла ошибка». В логе за эту минуту — 3000 строк от десятка запросов вперемешку. Нужна метка, которая связывает ответ клиенту и все строки лога одного запроса. Это и есть request_id.

РАЗБОР
КодЧто значитЗачем так
request.headers.get('X-Request-ID') or uuid4().hex[:12]взять готовый или создатьесли перед API стоит nginx или фронтенд уже сгенерировал id — один id пройдёт через всю цепочку
request.state.request_id«карман» запросаобработчики ошибок берут id оттуда: request.state.request_id
ContextVarпеременная, своя у каждой задачи asyncioлоггер не знает про request, а id нужен ему в каждой строке. Глобальная переменная перепутала бы id параллельных запросов

[-] — запись вне запроса (фоновое переподключение к RabbitMQ): значение ContextVar по умолчанию. Теперь по request_id из ответа клиента находим в логе все строки этого запроса: grep 5a0eb1014212 app.log.

?
ПОЧЕМУ НЕТ request_id_var.reset()

Аккуратный код со ContextVar обычно делает token = var.set(…) и в finally — var.reset(token). Здесь это сломает лог 500: обработчик Exception срабатывает после выхода из нашего middleware (он снаружи всех middleware), и увидел бы [-]. Сбрасывать и не нужно: uvicorn обрабатывает каждый запрос в своей задаче asyncio, а у задачи своя копия контекста.

Кто ловит первым: middleware или обработчик?

Методичка предлагает middleware с try/except Exception, который возвращает 500, — и рядом глобальный обработчик Exception. Проверим, как они уживаются. Отдельный файл, auth-api не трогаем:

Строка «сработал глобальный обработчик Exception» не появилась ни разу. Почему — видно по слоям приложения:

  запрос →  ServerErrorMiddleware       ← здесь живёт обработчик Exception (самый внешний слой)
              └ ваши middleware          ← try/except методички
                  └ ExceptionMiddleware  ← обработчики конкретных классов (AppError, HTTPException, 422)
                      └ роутер → эндпоинт  ← raise

Исключение всплывает изнутри наружу. Конкретные обработчики стоят ближе всех к эндпоинту — их ничто не перехватит. А Exception FastAPI отдаёт самому внешнему слою: до него ошибка дойдёт, только если по дороге её никто не поймал. Middleware с try/except ловит раньше — и глобальный обработчик становится мёртвым кодом.

✓
ПРАВИЛО

Выберите одно место для непредвиденных ошибок. В auth-api это обработчик Exception: он видит request, и его легко проверить тестом. Middleware делает то, что умеет только он: что-то до и после каждого запроса (id, время, заголовки), но не глотает исключения.

Проверяем на имитации GitHub

Всё, что клиенту знать не нужно (IP сервера, тело ответа GitHub), осталось в логе — и рядом с ним id запроса. 404 в лог не попал: это не ошибка сервера.

06 · Регистрация, когда RabbitMQ недоступен

live-coding~7 мин

Вспомним аудит: брокер лежит → клиент получил 400 с адресом объекта, а пользователь при этом создан. Что правильно ответить? Регистрация — главное действие, и оно удалось. Письмо «добро пожаловать» — второстепенное. Значит: 201, а сбой отправки события — в лог с traceback, чтобы его увидели и дослали.

Это тот самый оправданный except Exception из блока 02: мы знаем, что делать дальше (ответить 201), и не молчим (logger.exception).

А ПИСЬМО ТАК И НЕ УЙДЁТ?

Сейчас — нет, только строка в логе. Надёжное решение называется outbox: в той же транзакции, что и пользователя, записываем событие в таблицу outbox, а отдельная задача Celery раз в минуту отправляет неотправленные в RabbitMQ. Брокер лежит час — письма уйдут через час, но не потеряются. Это задание со звёздочкой.
