Введение в SQL и SELECT

Два урока PizzaHub брал меню из файла data/pizzas.json через «фейковый бэкенд». Сегодня заглянем туда, где данные живут по-настоящему, — в базу данных PostgreSQL. Научимся задавать ей вопросы на SQL и к концу урока соберём одним запросом всё, что в проекте сейчас делают три файла: фильтр, пагинатор и адаптер.

ЧТО СДЕЛАЕМ ЗА УРОК

  • Поймём, зачем базы данных, если есть JSON-файлы, и что такое СУБД, таблица, строка, колонка и тип.
  • Разберёмся с философией SQL: почему он «как React, а не как jQuery».
  • Поставим PostgreSQL и DBeaver, загрузим меню и заказы PizzaHub в настоящую базу.
  • Напишем запросы для каталога: SELECT, WHERE, AND/OR, NULL, DISTINCT, DISTINCT ON, ORDER BY, LIMIT/OFFSET, AS, LIKE/ILIKE.
  • Соберём финальный запрос «страница каталога»: категория + сортировка + страница + поля сразу в формате TypeScript-типа Pizza.

Часть 1 · Где живут данные

01 · Зачем база данных, если есть JSON?

теория~10 мин
База данных — хранилище, СУБД — программа-«библиотекарь», которая этим хранилищем управляет. А SQL — язык, на котором мы с библиотекарем разговариваем.

Начнём с нашего проекта

Сейчас меню PizzaHub лежит в файле data/pizzas.json, а fake-backend.ts читает его целиком. Для четырёх пицц — идеально. Теперь представьте настоящую доставку:

СитуацияJSON-файлБаза данных
В меню 4 пиццыотличноотлично
2 миллиона заказов, нужен заказ №1 873 004прочитать весь файл (гигабайты) в память и искать цикломнайдёт за миллисекунды по индексу
Два оператора одновременно меняют один заказкто последний сохранил файл, тот и прав. Изменения первого молча пропалитранзакции и блокировки: ничего не потеряется

База данных и СУБД — не одно и то же

  • База данных (БД) — сами данные, организованные по правилам. Книги на полках.
  • СУБД (система управления базами данных, англ. DBMS) — программа, которая хранит, ищет, защищает и меняет эти данные. Библиотекарь. PostgreSQL, MySQL, SQLite, Oracle — это СУБД.
 вы / бэкенд                       СУБД (PostgreSQL)               диск
 ┌──────────────┐  1. SQL-запрос    ┌────────────────────┐  3.  ┌──────────┐
 │ SELECT ...   │ ────────────────▶ │ разобрать запрос,  │ ───▶ │ 💾 файлы │
 │ FROM pizzas  │                   │ выбрать план,      │      │ базы     │
 │              │ ◀──────────────── │ проверить права    │ ◀─── │          │
 └──────────────┘  4. таблица-ответ └────────────────────┘      └──────────┘

Мы никогда не трогаем файлы базы руками. Мы вежливо просим библиотекаря на SQL, а он сам решает, на какую полку идти. Как fetch во фронтенде: вы не знаете, как сервер устроен внутри, вы отправляете запрос и получаете ответ.

ИСТОРИЯ: КАК SQL ПОЯВИЛСЯ И ПОЧЕМУ ORACLE НАЧИНАЛСЯ С ВЕРСИИ 2

1970 год. Математик из IBM Эдгар Кодд публикует статью «Реляционная модель данных для больших банков данных»: храните всё в простых таблицах и спрашивайте декларативно. Сама IBM не торопится — она хорошо зарабатывает на старой иерархической базе IMS. Её инженеры делают прототип и язык SEQUEL, но название приходится сменить на SQL: «Sequel» уже было торговой маркой британской авиастроительной компании.

Статьи IBM внимательно читает молодой программист Ларри Эллисон. Вместе с друзьями он выпускает коммерческую SQL-базу раньше самой IBM и называет её Oracle Version 2. Версии 1 не было никогда: «вторая версия» звучала надёжнее для покупателей. Так появилась одна из крупнейших компаний мира. А SQL с тех пор почти не изменился в основе: запросы из этого урока поняла бы и база 1990-х.

02 · Реляционная модель: таблицы, строки, типы

теория~8 мин

Реляционная (от relation — отношение) — значит, данные лежат в таблицах, которые можно связывать между собой. Ментальная модель: база — папка, таблицы — Excel-файлы в ней. Но есть одно главное отличие от Excel: у каждой колонки строгий тип.

Вот как будет выглядеть меню PizzaHub в базе (первые строки таблицы pizzas):

ПОЧЕМУ ЦЕНА В КОПЕЙКАХ

Посмотрите в data/pizzas.json: там тоже price_kopecks: 49900, а адаптер делит на 100. Это не прихоть. Дробные числа в компьютере хранятся приблизительно: в JS 0.1 + 0.2 === 0.30000000000000004. Для денег это недопустимо, поэтому их хранят целыми числами в минимальных единицах (копейках, центах). Так делают Stripe, ЮKassa и почти все платёжные API.

ГЛАВНОЕ ОТЛИЧИЕ ОТ TYPESCRIPT

Типы TypeScript живут только при компиляции: в рантайме в объект можно положить что угодно. Типы в базе проверяются при каждой записи. Попробуйте записать в price_kopecks строку 'дорого' — база ответит ошибкой и ничего не сохранит. Это последняя линия обороны данных.

03 · «Что», а не «как». Диалекты SQL

теория~7 мин

Главное, что нужно перестроить в голове: SQL — декларативный язык. Вы описываете результат, а не шаги.

Задача: найти пиццы дешевле 500 ₽. Вот как это выглядит на TypeScript:

Как именно база это найдёт — прочитает всю таблицу или воспользуется индексом, в каком порядке, сколько памяти взять — решает она сама. У неё есть специальный «планировщик», который выбирает самый быстрый путь.

★
ФРОНТЕНДЕРАМ ЭТО УЖЕ ЗНАКОМО

HTML и CSS — декларативные: вы пишете display: flex, а не вычисляете координаты каждого блока. React — декларативный: вы описываете, как должен выглядеть интерфейс при таком состоянии, а React сам решает, какие DOM-узлы поменять. jQuery — императивный: «найди элемент, поменяй класс, добавь узел». SQL для данных — то же, что React для интерфейса.

Диалекты

SQL — стандарт (ANSI/ISO), но каждая СУБД добавляет свои возможности. Так появляются диалекты:

СУБДГде встретитеРасширение языка
PostgreSQLбольшинство новых проектов, Supabase, NeonPL/pgSQL
MySQL / MariaDBWordPress, старые PHP-проекты—
SQLiteмобильные приложения, браузеры, Electron. Одна база = один файл—
Microsoft SQL Serverкорпоративный мир .NETT-SQL
Oracleбанки, госсекторPL/SQL

Ядро — SELECT, INSERT, UPDATE, DELETE, JOIN, транзакции — одинаково везде (стандарт SQL-92). Мы учим PostgreSQL, и примерно 95% знаний пригодятся в любой другой базе. Две «фишки только PostgreSQL» из этого урока — DISTINCT ON и ILIKE — я отмечу отдельно.

05 · SELECT и стиль запросов

live-coding~8 мин
SELECT — «покажи мне». Главная команда SQL: с неё начинается любое чтение данных.

Почему SELECT * — антипаттерн

Звёздочка значит «все колонки». Для того чтобы посмотреть на таблицу, — нормально. В коде приложения — нет:

  1. Лишняя работа и трафик. Нужны название и цена, а база читает и гонит по сети ещё описания, даты, веса. Для карточки в каталоге это килобайты мусора на каждую строку.
  2. Утечки. Классический баг: в таблице users есть password_hash, бэкенд делает SELECT * и отдаёт результат на фронт «как есть». Хеш пароля теперь виден во вкладке Network у любого пользователя.
  3. Хрупкость. Кто-то добавил в таблицу колонку — и ответ API внезапно изменился.

ЛОВУШКА: ЦЕЛОЧИСЛЕННОЕ ДЕЛЕНИЕ

Если обе части деления — целые числа, PostgreSQL отбрасывает дробную часть: SELECT 49950 / 100 вернёт 499, а не 499.5. В JS такого нет, там 49950 / 100 === 499.5. Чтобы получить дробь, сделайте одно из чисел дробным: 49950 / 100.0 → 499.5000000000000000. У нас все цены кратны 100, поэтому сейчас не заметно, но баг «пропали 50 копеек» — классика.

SQL Style Guide

Базе всё равно, как вы пишете: select pizza_name from pizzas сработает так же. Стиль нужен людям, которые будут читать запрос в код-ревью.

Так себе
select pizza_name, price_kopecks from pizzas where category = 'meat' order by price_kopecks;
Хорошо
SELECT pizza_name, price_kopecks
FROM pizzas
WHERE category = 'meat'
ORDER BY price_kopecks;
  1. Ключевые слова — ЗАГЛАВНЫМИ: SELECT, FROM, WHERE. Сразу видно, где команда, а где данные.
  2. Имена таблиц и колонок — snake_case: pizza_name, price_kopecks. Почему не camelCase — узнаем в блоке 10.
  3. Каждая часть запроса — с новой строки. Как Prettier для SQL. Подробнее — sqlstyle.guide (есть переводы, в том числе на русский).

БЕЗ ORDER BY ПАГИНАЦИЯ ЛОМАЕТСЯ

Мы помним из блока 07: без ORDER BY порядок не гарантирован. Значит, одна и та же пицца может попасть и на первую, и на вторую страницу, а другая — ни на одну. Пользователь видит дубли в ленте и «потерянные» товары. Второй подвох: сортировка только по цене, если у двух пицц одинаковая цена — их порядок снова случайный. Поэтому в конец ORDER BY добавляют уникальную колонку: ORDER BY price_kopecks, pizza_id.

☺
ПОЧЕМУ НИКТО НЕ ДОЛИСТЫВАЕТ ДО СТРАНИЦЫ 50 000

OFFSET 1000000 не «прыгает» к миллионной строке: база честно отсчитывает и выбрасывает миллион строк, прежде чем отдать вам 20. Чем дальше страница, тем медленнее. Поэтому в бесконечных лентах (Instagram, X) используют другой приём — «курсорную» пагинацию: «дай 20 записей, которые идут после записи с id = 4573». Её разберём в уроке про индексы.

                взять       отфильтровать   оставить       отсортировать   отрезать
                таблицу     строки          колонки,       результат       страницу
                                            посчитать AS

Это не теория ради теории — из порядка следует настоящая ошибка, на которую натыкаются все:

◆
ПОЧЕМУ ТАК

WHERE выполняется на шаге 2, а псевдоним price появляется только на шаге 3, в SELECT. Когда база фильтрует строки, колонки price ещё не существует. ORDER BY работает на шаге 4 — к этому моменту price уже есть. Как в JS: нельзя использовать const до строки, где он объявлен. В WHERE пишем полное выражение: WHERE price_kopecks < 50000.

Правило кавычек — главная ошибка JS-разработчиков

В JS 'Маргарита' и "Маргарита" — одно и то же. В SQL — две совершенно разные вещи:

11 · Поиск по сайту: LIKE и ILIKE

live-coding~7 мин

В шапке PizzaHub появляется строка поиска. Пользователь вводит «сыр» — нужно найти всё, где это слово встречается. Оператор = ищет только точное совпадение. Для частичного есть LIKE и шаблоны:

Символ шаблонаЗначитПример
%любое количество любых символов (и ноль тоже)'С%' — начинается на «С»; '%сыр%' — содержит «сыр»
_ровно один любой символ'_ыр%' — «сыр», «Сыр», «пыр»...

LIKE чувствителен к регистру: «сыр» и «Сыр» для него разные строки, поэтому «Сырная» не нашлась. Пользователь не обязан угадывать, с какой буквы мы написали название. Для поиска нужен ILIKE — Insensitive LIKE, нечувствительный к регистру. Это фишка PostgreSQL: в стандарте его нет, в других базах пишут LOWER(pizza_name) LIKE '%сыр%'.

РАЗБОР
КодЧто значитВ TypeScript

★
ЧЕСТНО ПРО ПОИСК

ILIKE '%...%' отлично подходит для меню на 16 пицц и для админок. На миллионе товаров он медленный (обычный индекс с % в начале не помогает) и не понимает словоформ: по запросу «сырный» не найдёт «сыр». Для настоящего поиска в PostgreSQL есть полнотекстовый поиск, а крупные магазины используют Elasticsearch или Meilisearch. Но 90% поисков в админках по-прежнему сделаны на ILIKE.

  4. Фильмы, в названии которых есть «air» в любом регистре. Проверка: 7 фильмов. Подумайте, почему LIKE '%air%' не находит ни одного.

  6. Короткие (меньше часа) дешёвые (rental_rate = 0.99) фильмы для детей (рейтинг 'G' или 'PG'), от коротких к длинным. Проверка: 17 фильмов.
  7. Сколько адресов без второй строки адреса? Сравните результаты WHERE address2 IS NULL и WHERE address2 = ''. Объясните разницу. Подсказка: SELECT count(*) FROM ... возвращает количество строк.
  8. Со звёздочкой: в задании 1 у трёх фильмов одинаковая длина. Сделайте порядок стабильным и объясните, зачем.
Ответы для преподавателя
-- 1
SELECT title, length FROM film
WHERE rating = 'R' AND length > 180
ORDER BY length DESC, title;
-- 2
SELECT DISTINCT rental_duration FROM film ORDER BY rental_duration;
-- 3
SELECT first_name AS "firstName", last_name AS "lastName"
FROM actor
ORDER BY last_name, first_name
LIMIT 10 OFFSET 10;
-- 4 (в Pagila все названия ЗАГЛАВНЫМИ: AIRPORT POLLOCK — поэтому LIKE '%air%' ничего не находит)
SELECT title FROM film WHERE title ILIKE '%air%' ORDER BY title;
-- 5
SELECT DISTINCT ON (customer_id) customer_id, amount, payment_date
FROM payment
ORDER BY customer_id, amount DESC, payment_date
LIMIT 5;
-- 6
SELECT title, rating, rental_rate, length FROM film
WHERE rating IN ('G', 'PG') AND rental_rate = 0.99 AND length < 60
ORDER BY length, title;
-- 7: IS NULL → 4, = '' → 599 (из 603). NULL («неизвестно») и пустая строка — разные значения
SELECT count(*) FROM address WHERE address2 IS NULL;
SELECT count(*) FROM address WHERE address2 = '';
