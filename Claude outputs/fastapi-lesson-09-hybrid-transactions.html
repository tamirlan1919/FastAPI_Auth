Гибридная архитектура и транзакции

За прошлые уроки в auth-api незаметно появились три хранилища: SQLite (пользователи, посты, теги, профили), MongoDB (задачи) и Redis (кеш и счётчики). Это уже гибридная архитектура, только мы её так не называли. Сегодня сначала разберёмся, почему так бывает и как жить с несколькими базами сразу. Потом спустимся в SQL и научимся трём вещам, которые отличают учебный проект от боевого: транзакции, избавление от N+1 и измерение запросов вместо гадания.

ЧТО ПОЯВИТСЯ В AUTH-API

  • Карта архитектуры проекта: что в какой базе лежит и почему; где у нас уже есть «двойная запись».
  • POST /auth/register-with-profile — пользователь и профиль создаются одной транзакцией: всё или ничего.
  • Счётчик SQL-запросов: в каждом ответе заголовки X-DB-Queries и X-DB-Time-ms.
  • API постов (модели и репозиторий уже есть, роутера не было): N+1 «как не надо» на ~60 запросов → жадная загрузка на 2.
  • GET /posts/stats — агрегации и подзапросы, закешированные в Redis.
  • GET /posts/export.csv — выгрузка потоком, без загрузки всех строк в память.
  • Индекс на posts.author_id через Alembic — и проверка через EXPLAIN, что он работает.

01 · Схема при записи и схема при чтении

теория~7 мин

Главное различие SQL и NoSQL — не синтаксис запросов, а вопрос «кто и когда проверяет форму данных».

✦
ИСТОРИЯ: АНКЕТА И ЕЖЕДНЕВНИК

SQL — это анкета в паспортном столе. Поля напечатаны заранее: фамилия, имя, дата рождения. Нельзя вписать «любимую пиццу» — для неё нет графы. Хотите новую графу — перепечатываете бланки для всех (миграция). Зато все анкеты одинаковые, и любую можно обработать вслепую.

NoSQL — это ежедневник. Пишите что хотите: сегодня список покупок, завтра телефон, послезавтра рисунок. Свобода! Но когда через год вы ищете «все телефоны», выясняется, что половина записана как «тел.», половина как «phone», а в одной — номер без кода города. Порядок наводит тот, кто читает.

◆
ГЛАВНАЯ МЫСЛЬ

У NoSQL схема никуда не исчезает — она переезжает из базы в код. В SQL дисциплину обеспечивает база, в NoSQL — вы сами. Поэтому «в Mongo нет схемы, это быстрее» — правда только на первых двух неделях проекта. Дальше вы платите за гибкость дисциплиной.

✦
ИСТОРИЯ: ОДИН ПОВАР ИЛИ ДЕСЯТЬ

Пиццерия не справляется с заказами. Вертикально: нанять шеф-повара, который готовит вдвое быстрее, и купить печь побольше. Работает, но лучшего повара в мире не наймёшь, а печь размером с дом не поставишь. Горизонтально: открыть ещё девять точек. Масштабируется бесконечно — но теперь, чтобы узнать «сколько всего продали “Пепперони”», нужно обзвонить все десять.

  • Почему SQL «растёт вверх». JOIN-ы и транзакции между таблицами — сильная сторона SQL, но они плохо работают, когда таблицы лежат на разных серверах. Поэтому SQL-базу обычно сначала усиливают, а нагрузку на чтение снимают репликами — копиями только для чтения.
  • Почему NoSQL «растёт вширь». Документ самодостаточен: всё, что нужно, лежит внутри. Его можно целиком положить на любой узел — отсюда простое шардирование.
!
ПРАВДА ЖИЗНИ

Граница давно размыта: PostgreSQL шардируют (Citus), у MongoDB есть ACID-транзакции. А одного хорошего сервера PostgreSQL хватает на десятки тысяч запросов в секунду — подавляющему большинству проектов шардирование не понадобится никогда. Масштабирование — аргумент в выборе базы, только когда у вас реально миллионы пользователей, а не «а вдруг».

НАХОДКА В НАШЕМ КОДЕ

В users.py есть эндпоинт GET /users/mongo/me, который читает коллекцию users из MongoDB. Значит, пользователи теперь живут в двух базах. Какая из них главная? Если сменить email через SQL, обновится ли Mongo? Нет. Это классическая проблема гибридных систем, и у неё есть правило: у каждой сущности ровно один «источник правды». Остальные хранилища — только копии, которые синхронизируются от него. Как именно — в следующем блоке.

Подключение к нескольким базам в FastAPI у нас уже сделано правильно: каждая база — своя зависимость (SessionDep, RedisDep), и эндпоинт просит ровно то, что ему нужно. MongoDB пока подключена глобальной переменной database — в домашке переведём её на зависимость, как Redis.

05 · Как синхронизировать базы

теория~8 мин

Стратегия 1. Общий идентификатор

Сущность живёт в одной базе, а в других хранится только её ID. Например, задача в Mongo хранит owner_id = users.id из SQL. В нашем todos такого поля пока нет — задачи ничьи; добавим его в домашке. Связь через ID — без дублирования данных. Внешнего ключа между разными базами не бывает, поэтому за целостность отвечает приложение.

Стратегия 2. Двойная запись (dual write)

Приложение само пишет в обе базы подряд. И у нас это уже есть: сегодня при регистрации и создании поста мы будем делать COMMIT в SQL, а затем DELETE ключа в Redis.

  1. SQL:   INSERT + COMMIT    ✅  — данные сохранены навсегда
  2. Redis: DEL users:all      💥  — сеть моргнула, ключ не удалился

  Итог: в базе новый пользователь, в кеше — старый список. Ещё до 60 секунд (TTL) API отдаёт устаревшее.
◆
ПОЧЕМУ ДЛЯ КЕША ЭТО НОРМАЛЬНО, А ДЛЯ ДЕНЕГ — НЕТ

Общей транзакции на две разные базы не бывает: SQLite ничего не знает про Redis. Значит, между двумя записями всегда есть момент, когда одна прошла, а вторая — ещё нет (или уже никогда). Для кеша это терпимо: TTL сам исправит рассинхрон. Для «списали деньги в SQL, начислили бонусы в Mongo» — нет: бонусы потеряются навсегда. Порядок «сначала источник правды, потом копия» хотя бы гарантирует, что потеряется копия, а не оригинал.

Стратегия 3. События через очередь (event-driven)

Приложение пишет только в главную базу и публикует событие «заказ создан» в брокер сообщений (RabbitMQ, Kafka, Redis Streams). Отдельный обработчик (consumer) получает событие и обновляет вторую базу. Упал обработчик — событие подождёт в очереди и будет обработано позже.

 FastAPI ──1. INSERT заказ + COMMIT──▶ [ PostgreSQL ]
    │
    └──2. publish «order_created»──▶ [ Брокер ] ──3. доставить──▶ [ Worker ] ──4. обновить──▶ [ MongoDB ]
                                     событие лежит,                       упал? повторит
                                     пока его не заберут
☺
ПОДВОХ ДЛЯ ВНИМАТЕЛЬНЫХ

А если приложение упало между шагами 1 и 2? Заказ в базе есть, а события нет — снова двойная запись, только с брокером вместо Mongo! Профессиональное решение называется Transactional Outbox: событие пишется в ту же SQL-базу, в таблицу outbox, в той же транзакции, что и заказ. А отдельный процесс читает outbox и отправляет события в брокер. Транзакция гарантирует: есть заказ ⇔ есть событие. Это хороший вопрос на собеседовании уровня middle.

06 · Транзакция и ACID

теория~8 мин
Транзакция — несколько операций с базой, которые выполняются как одна: либо все, либо ни одной.COMMIT — зафиксировать всё. ROLLBACK — откатить всё, как будто ничего не было.
✦
ИСТОРИЯ: БАНКОМАТ

Вы переводите другу 1000 ₽. Банк должен сделать две вещи: списать у вас и начислить ему. Представьте, что после списания в серверной выбило пробки. Без транзакции деньги просто исчезли: у вас минус, у друга ничего. С транзакцией после перезапуска база видит незавершённую операцию и откатывает списание. Деньги на месте, вы пробуете ещё раз.

ACID — четыре обещания базы

БукваЧто обещаетНа примере перевода
Atomicity — атомарностьвсё или ничегонет состояния «списали, но не начислили»
Consistency — согласованностьпосле транзакции все правила базы соблюденыUNIQUE, NOT NULL, FOREIGN KEY не нарушены — иначе откат
Isolation — изолированностьпараллельные транзакции не видят «полуготовые» данные друг другаотчёт по балансам не увидит момент, когда деньги «в пути»
Durability — долговечностьпосле COMMIT данные не пропадутвыключили свет через секунду после «Перевод выполнен» — перевод на месте
☺
ЗАПОМИНАЛКА

ACID по-английски — «кислота». Шутят, что NoSQL-базы долго были «щелочными» — BASE: Basically Available, Soft state, Eventually consistent («в целом доступна, состояние может плавать, когда-нибудь станет согласованным»). Кислота против щёлочи — химики оценили бы. С тех пор многие NoSQL-базы получили ACID-транзакции, но название осталось как способ описать два разных подхода.

Транзакции в SQLAlchemy: три вещи, которые нужно знать

  1. Autobegin. Сессия начинает транзакцию сама при первом запросе. В логах echo=True вы постоянно видели строку BEGIN (implicit) — это она.
  2. flush() ≠ commit(). flush отправляет накопленные INSERT/UPDATE в базу внутри транзакции — например, чтобы узнать id новой строки. Но это ещё не навсегда: ROLLBACK отменит и их. Навсегда — только commit.
  3. async with session.begin(): — рекомендуемый способ. Вышли из блока без ошибок — COMMIT; вылетело исключение — ROLLBACK и исключение летит дальше. Забыть сделать rollback невозможно.
гдеСейчас ничего не пишем — просто сравниваем. Способ 1 у вас уже есть в app/repositories/user_repo.py (метод create). Способ 2 напишем руками в блоке 07, в новом файле app/services/registration_service.py.

07 · Регистрация с профилем в одной транзакции

live-coding~13 мин

Боль: репозитории сами делают commit

В проекте есть UserRepo.create (app/repositories/user_repo.py) и ProfileRepo.create (app/repositories/profile_repo.py). Хотим регистрацию «сразу с профилем» — первая мысль: вызвать их по очереди. Но посмотрите внутрь: каждый метод заканчивается на await self.session.commit().

◆
ГДЕ ДОЛЖЕН ЖИТЬ COMMIT

Репозиторий не знает, частью какой бизнес-операции он является. Решение «всё, операция закончена, фиксируем» должен принимать тот, кто видит операцию целиком, — сервис (или эндпоинт). Этот принцип называется Unit of Work: репозитории только добавляют и читают, а сервис открывает транзакцию и закрывает её одним COMMIT. Существующие методы мы трогать не будем — регистрация /auth/register продолжит работать как была. Новую операцию напишем правильно.

  • Выход из блока → INSERT INTO profiles + COMMIT. Благодаря expire_on_commit=False в нашем database.py объект user остаётся читаемым и после коммита.

ЛОВУШКА: «A TRANSACTION IS ALREADY BEGUN»

session.begin() работает только на «чистой» сессии. Если в этом же запросе сессия уже что-то читала, транзакция уже открыта (autobegin), и вы получите InvalidRequestError: A transaction is already begun on this Session. Типичный случай — эндпоинт с CurrentUserDep: get_current_user уже сходил в базу через ту же сессию (FastAPI отдаёт одну и ту же сессию всем зависимостям одного запроса). В таких эндпоинтах либо делайте await session.commit() / rollback() явно, либо async with session.begin_nested(): — вложенная транзакция (SAVEPOINT).

А ГОНКИ?

Два запроса одновременно регистрируют одного и того же pizza_lover: оба делают SELECT — «свободно», оба делают INSERT. Спасёт unique=True на username и email в модели: второй INSERT упадёт с IntegrityError, и транзакция откатится. Проверка в коде — для красивого сообщения, уникальный индекс в базе — для гарантии. Для «списать со склада» в PostgreSQL используют блокировку строки: select(Item).where(...).with_for_update() (в SQLite её нет — там блокируется вся база на запись).

Шаг 3. Как НЕ надо: N+1

✦
ИСТОРИЯ: ПОХОД В МАГАЗИН

Вам нужно купить продукты по списку из 50 пунктов. Вариант «N+1»: сходить в магазин за списком, вернуться, сходить за молоком, вернуться, сходить за хлебом, вернуться… 51 поход. Вариант «жадная загрузка»: взять корзину и купить всё за один раз. SQL-запрос по сети — это поход в магазин.

создаёмapp/api/routers/posts.pyчтоНачинаем с импортов и учебного «плохого» эндпоинта. Остальное добавим ниже по ходу урока.

1 запрос за постами + 50 за тегами + ещё по запросу на каждого нового автора. Почему авторов меньше 50? session.get() сначала смотрит в identity map — «записную книжку» сессии: если пользователь с таким id уже загружен, второй раз в базу за ним не ходят. Число у вас может немного отличаться, но порядок тот же: около 60.

!
А ПОЧЕМУ НЕ ПРОСТО post.author?

В синхронном SQLAlchemy (и в Django) обращение post.author внутри цикла тихо сделает запрос — это «классический» N+1, который годами живёт незамеченным. В async SQLAlchemy такое обращение без предварительной загрузки сразу падает: MissingGreenlet: greenlet_spawn has not been called; can't call await_() here. Неприятно, но честно: async-режим заставляет думать о загрузке связей заранее. В «плохом» эндпоинте мы поэтому сделали лишние запросы явно — чтобы их было видно.

Разбор от простого к сложному

  • count_all — самое простое: SELECT count(posts.id) FROM posts. session.scalar() возвращает сразу одно значение, без .scalars().first().
  • count_by_tag — JOIN тегов с таблицей связей post_tags и GROUP BY по имени тега: «для каждого тега посчитай строки». .label("posts") — имя колонки в результате, как AS posts.
  • top_authors — то же самое для авторов плюс ORDER BY ... DESC LIMIT 5.
  • avg_posts_per_author — среднее от количеств. Нельзя написать AVG(COUNT(...)) — агрегаты не вкладываются. Поэтому сначала подзапрос «сколько у каждого автора» (.subquery() — превращается в FROM (SELECT ...)), а потом AVG по нему.
  • authors_above_average — самый сложный: подзапрос «посты по авторам» используется дважды — один раз для JOIN с users (получить имена), второй — внутри .scalar_subquery() для среднего, с которым сравниваем в WHERE.

11 · Большие объёмы: выгрузка потоком

live-coding~7 мин

Бухгалтерия просит CSV со всеми постами. Сегодня их 300, через год — 3 миллиона. .all() загрузит все строки в память сервера сразу, а потом ещё соберёт гигантскую строку CSV. Это прямой путь к тому, что процесс убьют по нехватке памяти.

✦
ИСТОРИЯ: ВОДОПРОВОД

Чтобы наполнить бассейн, не нужно сначала привезти всю воду в цистерне. Открываете кран — вода идёт по трубе понемногу и сразу в бассейн. Потоковая выгрузка устроена так же: читаем из базы порцию → отправляем клиенту → читаем следующую. В памяти всегда одна порция.

  • select(Post.id, Post.title, User.username) — только нужные колонки, а не целые ORM-объекты: меньше памяти, никаких связей.
  • session.stream(stmt) — вместо execute: результат читается из базы по мере надобности, а не весь сразу. yield_per=100 — порции по 100 строк.
  • result.partitions(100) — асинхронно отдаёт списки по 100 строк. Каждую порцию превращаем в кусок CSV и сразу yield клиенту.
  • StreamingResponse принимает генератор и отправляет ответ кусками, по мере того как генератор их выдаёт. Content-Disposition: attachment — браузер скачает файл.
  • Почему своя сессия, а не SessionDep? Генератор работает, пока ответ отправляется, — уже после того, как эндпоинт вернул StreamingResponse. Сессия из зависимости к этому моменту может быть закрыта. Поэтому сессия открывается внутри генератора и живёт ровно столько, сколько поток.
Проверка: откройте в браузере http://localhost:8000/posts/export.csv — скачается файл на 301 строку (заголовок + 300 постов). x-db-queries у этого ответа будет 0: запросы идут уже после того, как middleware отработал, — ещё одна иллюстрация того, что поток живёт дольше эндпоинта.

12 · EXPLAIN и индекс через Alembic

live-coding~9 мин

Мы научились считать запросы. Теперь узнаем, как база выполняет один запрос. Для этого есть EXPLAIN — «покажи план, не выполняя». В PostgreSQL это EXPLAIN ANALYZE (план + реальное время), в SQLite — EXPLAIN QUERY PLAN.

✦
ИСТОРИЯ: ПРЕДМЕТНЫЙ УКАЗАТЕЛЬ

Найти в учебнике всё про «транзакции» можно двумя способами: листать все 600 страниц (SCAN — полный перебор) или открыть предметный указатель в конце: «Транзакции — стр. 214, 389» (SEARCH USING INDEX). Индекс — это и есть предметный указатель для столбца.

!
НАХОДКА В НАШЕЙ СХЕМЕ

По author_id мы ищем постоянно: PostRepo.get_by_author, JOIN в статистике. А индекса на этом столбце нет! Многие думают, что ForeignKey создаёт индекс автоматически. Нет — ни SQLite, ни PostgreSQL не индексируют внешний ключ сами (MySQL — индексирует). Это одна из самых частых причин медленных JOIN в проде.

меняемapp/db/models.pyчтоОдно слово в модели Post: index=True у author_id.

Помним правило из урока 6: читаем миграцию глазами перед применением. Здесь всё правильно: одна операция, и downgrade её отменяет.

◆
ЦЕНА ИНДЕКСА

Индекс ускоряет чтение, но замедляет каждую запись (INSERT/UPDATE/DELETE обновляют и таблицу, и все её индексы) и занимает место. Индексируем столбцы, по которым реально ищем, джойним и сортируем, — и проверяем EXPLAIN, а не ставим index=True везде «на всякий случай». В PostgreSQL ищите в плане Seq Scan на большой таблице — это и есть «листаем все 600 страниц».
