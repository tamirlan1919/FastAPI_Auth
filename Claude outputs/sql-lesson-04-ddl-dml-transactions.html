Три урока мы только читали данные — сегодня начнём их создавать и менять. Видеопрокат хочет две новые функции: отзывы о фильмах и бонусный кошелёк, бонусы с которого можно дарить друг другу. 01 · DDL и DML, типы данных

теорияlive~10 мин

Все команды SQL делятся на несколько «языков». Нам сегодня нужны два:

ГруппаЧто делаетКомандыАналогия с фронтендом
DDL — Data Definition Languageописывает структуру: какие таблицы, колонки, правилаCREATE, ALTER, DROP, TRUNCATETypeScript-интерфейс: interface Review { rating: number }
DML — Data Manipulation Languageработает с данными внутри структурыSELECT, INSERT, UPDATE, DELETEсами объекты: { rating: 5 }

Разница с TypeScript важная: TypeScript проверяет типы только при сборке, а в браузер уходит обычный JS. База проверяет типы и правила при каждой записи, всегда. Её не обойти никаким кодом.

ФРОНТЕНДЕРАМ ЭТО ЗНАКОМО

Откройте консоль браузера: 0.1 + 0.2 → 0.30000000000000004. Тот же стандарт IEEE 754, та же ошибка. Поэтому на фронте деньги считают в копейках (1099 вместо 10.99) или через библиотеки вроде decimal.js, а в базе используют NUMERIC. В JSON из API деньги часто приходят строкой "10.99" — именно чтобы JavaScript не испортил число.

→
TIMESTAMP ИЛИ TIMESTAMPTZ

TIMESTAMP хранит «10:00» без пояса: непонятно, это 10:00 в Москве или в Нью-Йорке. TIMESTAMPTZ хранит точный момент (внутри — в UTC) и показывает его в поясе вашего подключения. Поэтому мы и пишем SET TIME ZONE 'UTC' в начале скрипта. Правило простое: для моментов времени (создан, оплачен) — всегда TIMESTAMPTZ.

Ломаем каждое правило

Теперь представим, что на фронте баг: форма отправляет что попало. Выполняйте запросы по одному (Ctrl+Enter) — каждый должен упасть.

База отвергла все пять. Обратите внимание на имена в ошибках: film_review_rating_check, film_review_customer_id_film_id_key — PostgreSQL сам придумал их по шаблону «таблица_колонки_тип». На бэкенде по такому имени ошибку превращают в понятный ответ API: «Вы уже оставили отзыв на этот фильм» вместо «Internal Server Error».

◆
ЗАЧЕМ ПРОВЕРЯТЬ В БАЗЕ, ЕСЛИ ЕСТЬ ВАЛИДАЦИЯ НА ФРОНТЕ?

Валидация на фронте — для удобства пользователя: подсказать до отправки. Но в базу пишет не только ваша форма: мобильное приложение, старая версия сайта, скрипт импорта, коллега из консоли, злоумышленник через Postman. CHECK, UNIQUE и NOT NULL — последняя линия обороны, которую не обойти. А UNIQUE вообще нельзя надёжно проверить в коде: два запроса одновременно спросят «есть ли отзыв?», оба получат «нет» и оба запишут.

☺
КУДА ДЕЛИСЬ НОМЕРА 2, 3, 4, 5?

Второй отзыв получил номер 6, а не 2. Номера 2–5 «съели» неудачные вставки 6a–6d: база выдала номер, а потом строка не прошла проверку. Посмотрите на DETAIL ошибок 6a и 6d: там видны (2, ...) и (5, ...). Счётчик никогда не откатывается назад — это сделано специально, чтобы тысячи одновременных вставок не ждали друг друга. Дыры в id — норма. Если менеджер просит «пронумеровать заказы без пропусков», это отдельная задача, и id для неё не подходит.

03 · ALTER TABLE и миграции

live-coding~12 мин

Прошла неделя, приходят новые требования: пометка «спойлер», дата редактирования, а колонку body хотят переименовать в review_text. Пересоздать таблицу нельзя — в ней уже живые отзывы. Для этого есть ALTER TABLE.

Логично: у двух существующих отзывов значения нет, а колонка обязательна. Правильный рецепт — в три шага: добавить необязательную колонку, заполнить, сделать обязательной.

Смена типа упала: «Отличный фильм, пересмотрю» не помещается в 10 символов. База не стала молча обрезать текст — и это хорошо. Ограничение длины лучше делать через CHECK: его можно добавить, убрать и поменять, не трогая тип. Колонку moderated_at мы создали для примера — удалим её.

ШПАРГАЛКА ALTER TABLE
КодЧто делаетОпасность
ADD COLUMN x TYPE [DEFAULT ...]добавить колонкунизкая. С NOT NULL нужен DEFAULT или рецепт из трёх шагов
RENAME COLUMN a TO bпереименоватьмгновенно, но ломает код, который пишет a
ALTER COLUMN x TYPE ...сменить типможет упасть или тихо изменить данные (см. ниже); на большой таблице перезаписывает её целиком

ADD CONSTRAINT имя CHECK (...)добавить правилопроверяет все существующие строки

Ни ошибки, ни предупреждения: ALTER COLUMN balance TYPE INTEGER молча округлит каждый баланс. У одних клиентов бонусы «появятся», у других пропадут.

Миграции

На реальном проекте никто не пишет ALTER TABLE руками в продакшен-базу. Каждое изменение структуры оформляют как миграцию — файл в репозитории, который применяется автоматически при деплое на всех серверах по порядку. Это git для структуры базы.

В Node.js такие файлы создаёт Prisma (npx prisma migrate dev), TypeORM или Knex, в Python — Alembic (его мы используем в FastAPI-проекте). Внутри — тот же SQL, который мы сейчас писали руками.

!
ALTER TABLE БЛОКИРУЕТ ТАБЛИЦУ

Большинство команд ALTER TABLE берут самую сильную блокировку: пока команда работает, таблицу нельзя ни читать, ни писать. На нашей таблице из двух строк это миллисекунды. А смена типа колонки в таблице на 50 миллионов заказов перезаписывает её целиком — сайт может «лежать» минуты. Поэтому большие миграции делают по шагам, как в рецепте с NOT NULL, и в часы наименьшей нагрузки.

live-coding~14 мин

Одну строку мы уже вставляли. Три способа, которые нужны на практике: несколько строк за раз, вставка с возвратом результата и вставка из запроса.

Когда фронт отправляет POST /api/reviews, а сервер в ответ присылает { "review_id": 7, "created_at": "..." } — это почти наверняка INSERT ... RETURNING. Prisma делает так при каждом prisma.review.create().

INSERT ... SELECT: данные из запроса

Задача: для тестов нужны отзывы. Пусть клиенты 5–9 «оценят» все фильмы, которые брали: брали повторно — 5 звёзд, один раз — 3. Привычка из урока 3: сначала SELECT, смотрим, что получится, и только потом вставляем.

355 строк одной командой, без единой строчки кода на JavaScript. INSERT 0 355 — так база сообщает, сколько строк вставлено (0 — исторический артефакт, всегда ноль). Колонки SELECT сопоставляются со списком в INSERT по порядку, а не по именам.

Вторая таблица: бонусный кошелёк

Начислим каждому клиенту приветственные бонусы — 5% от всех его платежей. Этот кошелёк понадобится во второй части для транзакций.

05 · UPDATE, DELETE, TRUNCATE и мягкое удаление

live-coding~12 мин

Клиент №3 передумал: фильм №2 уже не кажется ему скучным. Правило, которое стоит выучить раньше синтаксиса: перед UPDATE и DELETE выполните SELECT с тем же WHERE и посмотрите, какие строки изменятся.

РАЗБОР
КодЧто значитЗачем так
UPDATE film_reviewкакую таблицу меняемодна таблица за раз
SET a = ..., b = ...новые значения через запятуюсправа можно писать выражения: balance = balance + 10

UPDATE по данным из других таблиц

Акция: всем клиентам из Канады +10 бонусов. Страна живёт через три таблицы от кошелька — нужна цепочка JOIN из урока 3. В UPDATE для этого есть FROM.

Проверка показала 5 клиентов — и UPDATE 5 изменил ровно 5 строк. Числа совпали, значит условие верное. Связь с обновляемой таблицей пишется в WHERE (c.customer_id = w.customer_id), а не в ON: таблица bonus_wallet стоит в UPDATE, а не в FROM. Общая сумма бонусов теперь 8548,37 + 50 = 8598,37.

Забытый WHERE

✦
ИСТОРИЯ: «ПОЧЕМУ У ВСЕХ ПОЛЬЗОВАТЕЛЕЙ ОДИН ПАРОЛЬ?»

Классика, которую рассказывают в каждой второй команде: разработчик сбрасывает пароль одному пользователю, выделяет в редакторе UPDATE users SET password_hash = '...', нажимает «выполнить» — а строка WHERE id = 42 осталась невыделенной. Через минуту у всех пользователей одинаковый пароль, а в чате — «а почему я могу войти в чужой аккаунт?». Три привычки, которые защищают:

1) сначала SELECT с тем же WHERE; 2) опасные изменения — внутри BEGIN: проверили число строк и только потом COMMIT; 3) в DBeaver есть защита: у подключения на вкладке General выберите тип Production — тогда DBeaver будет спрашивать подтверждение перед каждым изменением данных.

НИКОГДА НЕ ПИШИТЕ TRUNCATE ... CASCADE НА АВТОМАТЕ

Подсказка из ошибки выглядит невинно: «используйте TRUNCATE ... CASCADE». Но она очистит не только customer, а все таблицы, которые на него ссылаются: платежи, аренды, наши отзывы и кошельки. Вся бизнес-история проката — одной командой.

На практике данные пользователей почти никогда не удаляют физически. Их помечают как удалённые — это мягкое удаление (soft delete), о нём шла речь в уроке 3. В Pagila для этого есть колонка customer.activebool:

12 клиентов «удалены», но их платежи, аренды и история на месте. «Удалить» становится UPDATE customer SET activebool = false WHERE ..., а все запросы приложения получают условие WHERE activebool. Плюс: можно восстановить аккаунт и не ломается бухгалтерия. Минус: это условие легко забыть в каком-нибудь запросе.

06 · UPSERT: вставить или обновить

live-coding~8 мин

Фронтенд отправляет оценку: клиент нажал звёздочку. Если он ещё не оценивал фильм — нужна новая строка, если оценивал — обновить старую. Можно сделать SELECT, а потом в коде выбрать INSERT или UPDATE. Но это два запроса, и между ними второй запрос (двойной клик!) успеет вставить строку — получим ошибку duplicate key. PostgreSQL умеет сделать это одной атомарной командой.

Новый отзыв получил номер 366, хотя до этого последним был 364. Номер 365 «съел» запрос 28: база выдала номер ещё до того, как обнаружила конфликт. Тот же эффект, что в блоке 02.

ИДЕМПОТЕНТНОСТЬ

Запрос 29 можно выполнить хоть десять раз — результат один: один отзыв с оценкой 4. Такие операции называют идемпотентными. Это важно, потому что сеть ненадёжна: фронт отправил запрос, ответ потерялся, fetch повторил запрос (или пользователь нажал кнопку дважды). С обычным INSERT второй запрос упадёт или создаст дубль, с UPSERT — ничего не испортит. Поэтому, например, PUT в REST по договорённости должен быть идемпотентным, а POST — нет.

07 · Транзакции и ACID

live-coding~15 мин

Новая функция: клиент может подарить бонусы другу. Перевод — это два UPDATE: списать у одного и начислить другому. Что будет, если между ними что-то сломается? Сначала проверим без защиты.

Обратите внимание: UPDATE 0 — не ошибка. База честно выполнила «увеличь баланс всем клиентам с id 99999» — таких нет. А вместо опечатки мог быть сбой: упал сервер приложения, оборвалась сеть, закончилась память. Списание уже записано, начисления не будет никогда. Вернём бонусы и сделаем правильно.

Транзакция: всё или ничего

  BEGIN ─────────────── «черновик» ───────────────── COMMIT
    │   UPDATE  −5 клиенту 1                            │   изменения видят все,
    │   UPDATE  +5 клиенту 2                            │   они записаны на диск
    │   другие подключения видят СТАРЫЕ балансы          │
    │                                                   │
    └── ошибка / ROLLBACK / обрыв связи / сервер упал ──┴──▶ всё отменено, как будто
                                                             транзакции не было

Теперь главный эксперимент: клиент 1 пытается подарить 100 бонусов, хотя у него 5,87. Начисление мы специально поставили первым — оно пройдёт.

Сработали две защиты сразу. CHECK (balance >= 0) из блока 04 не дал уйти в минус. А транзакция отменила начисление +100, которое уже прошло. Строка current transaction is aborted — важное поведение PostgreSQL: после любой ошибки транзакция «сломана», все следующие команды игнорируются, и единственный выход — ROLLBACK. Даже если написать COMMIT, база выполнит откат.

!
DBEAVER: AUTO-COMMIT

По умолчанию DBeaver работает в режиме Auto-commit: каждая команда — отдельная транзакция, которая сразу фиксируется. Поэтому запрос 32 сразу «потерял» бонусы. Явный BEGIN временно отключает это до COMMIT/ROLLBACK. На панели инструментов есть переключатель режима Auto-Commit / Manual Commit: в ручном режиме ничего не фиксируется, пока вы не нажмёте кнопку Commit. А если забыли COMMIT и закрыли DBeaver, он спросит, что сделать с незавершённой транзакцией. Незакрытая транзакция держит блокировки, и другие запросы будут её ждать — это увидим в блоке 08.

ACID: четыре обещания базы

БукваОбещаниеЧто мы видели
A — Atomicity, атомарностьвсе команды транзакции выполняются целиком или не выполняются вовсезапрос 34: +100 откатилось вместе с ошибкой
C — Consistency, согласованностьпосле транзакции все правила (CHECK, FK, UNIQUE) соблюденыбаланс не стал −94,13
I — Isolation, изоляцияпараллельные транзакции не видят «черновики» друг другаблок 08
D — Durability, надёжностьпосле COMMIT данные переживут выключение сервераPostgreSQL сначала записывает изменения в журнал на диске (WAL), и только потом отвечает «COMMIT»

SAVEPOINT: откатить часть транзакции

Клиент 1 дарит 1 бонус клиенту 2 и заодно оставляет отзыв «Спасибо за подарок!». Если отзыв не сохранится, подарок отменять не хочется. SAVEPOINT — «точка сохранения», как в игре: можно вернуться к ней, не теряя всё, что было до неё.

ROLLBACK TO SAVEPOINT откатил только неудачный INSERT и «починил» сломанную транзакцию, а COMMIT зафиксировал перевод. Без SAVEPOINT ошибка отзыва отменила бы и подарок.

★
КАК ЭТО ВЫГЛЯДИТ В КОДЕ

В Node.js вы редко пишете BEGIN руками: ORM делает это сама. В Prisma перевод выглядит так 👀: await prisma.$transaction(async (tx) => { await tx.bonusWallet.update({ where: { customerId: 1 }, data: { balance: { decrement: 5 } } }); await tx.bonusWallet.update({ where: { customerId: 2 }, data: { balance: { increment: 5 } } }); }). Если внутри функции бросить исключение, Prisma сделает ROLLBACK, иначе — COMMIT. В FastAPI-проекте то же самое делает async with session.begin():. А decrement: 5 превращается в SET balance = balance - 5 — почему это важно, увидим прямо сейчас.

08 · Два пользователя сразу: блокировки и потерянное обновление

live-coding~10 мин

Пока мы работали в одном окне. А на сервере одновременно работают сотни подключений. Откройте второе окно: SQL Editor → New SQL script ещё раз (или Ctrl+]). Первое окно — «пользователь A», второе — «пользователь B». Положите окна рядом и выполняйте команды по одной, в указанном порядке.

!
ПРОВЕРЬТЕ, ЧТО ОКНА — РАЗНЫЕ ПОДКЛЮЧЕНИЯ

По умолчанию DBeaver открывает для каждого редактора отдельное подключение. Если на шаге 3 первого опыта запрос в окне B не «завис», значит окна делят одно подключение: включите Window → Preferences → Editors → SQL Editor → Open separate connection for each editor и переподключитесь. Запасной вариант — второе окно в терминале: docker exec -it <контейнер> psql -U postgres -d pagila (имя контейнера покажет docker ps).

Опыт 1. Изоляция и блокировка строки

ШагОкно AОкно BЧто видим
1BEGIN;
UPDATE bonus_wallet SET balance = balance - 2 WHERE customer_id = 1;		A списал 2 бонуса, но не зафиксировал
2SELECT balance FROM bonus_wallet WHERE customer_id = 1;4.87 — B не видит черновик A (буква I в ACID)
3UPDATE bonus_wallet SET balance = balance - 1 WHERE customer_id = 1;запрос B висит: строку держит A
4SELECT balance FROM bonus_wallet WHERE customer_id = 1;2.87 — A видит свой черновик
5COMMIT;в ту же секунду UPDATE в B выполнился
6SELECT balance FROM bonus_wallet WHERE customer_id = 1;1.87 = 4.87 − 2 − 1. Оба списания учтены

В моём прогоне запрос B ждал 3,5 секунды — ровно до COMMIT в A. Когда две транзакции меняют одну строку, вторая ждёт первую. Читать при этом можно свободно: читатели не ждут писателей.

Опыт 2. Потерянное обновление

Теперь сделаем так, как часто пишут новички: прочитали баланс в приложение, посчитали новое значение на JavaScript и записали готовое число. A дарит 5 бонусов, B дарит 3 — с одного кошелька клиента №2, одновременно.

ШагОкно A (дарит 5)Окно B (дарит 3)Что видим
1BEGIN;
SELECT balance FROM bonus_wallet WHERE customer_id = 2;		BEGIN;
SELECT balance FROM bonus_wallet WHERE customer_id = 2;		оба прочитали 18.77
2«в JS» 18.77 − 5 = 13.77:
UPDATE bonus_wallet SET balance = 13.77 WHERE customer_id = 2;
COMMIT;
3«в JS» 18.77 − 3 = 15.77:
UPDATE bonus_wallet SET balance = 15.77 WHERE customer_id = 2;
COMMIT;
4SELECT balance FROM bonus_wallet WHERE customer_id = 2;15.77, а должно быть 10.77

Клиент подарил 8 бонусов, а списалось 3. Подарок A потерян: B перезаписал баланс числом, посчитанным по устаревшим данным. Транзакции не помогли — каждая сама по себе прошла корректно. Это lost update, одна из самых частых ошибок в бэкенде: лайки, остатки на складе, счётчики просмотров.

РешениеКакКогда
1. Считать в базеSET balance = balance - 5 вместо SET balance = 13.77почти всегда. Так работает опыт 1: база сама берёт актуальное значение под блокировкой
2. Заблокировать при чтенииSELECT ... FOR UPDATE — «читаю, чтобы изменить: остальные подождите»когда решение принимается в коде: «хватает ли бонусов? есть ли товар на складе?»

Проверим второе решение. Сначала вернём баланс: UPDATE bonus_wallet SET balance = 18.77 WHERE customer_id = 2; — и повторим опыт, добавив к обоим SELECT слова FOR UPDATE:

ШагОкно AОкно BЧто видим
1BEGIN;

2BEGIN;
SELECT balance FROM bonus_wallet WHERE customer_id = 2 FOR UPDATE;		B висит на чтении
3UPDATE bonus_wallet SET balance = 13.77 WHERE customer_id = 2;
COMMIT;		B сразу получил 13.77 — свежее значение
413.77 − 3 = 10.77:
UPDATE bonus_wallet SET balance = 10.77 WHERE customer_id = 2;
COMMIT;		итог 10.77 — оба подарка учтены

Опыт 3. Взаимная блокировка (deadlock)

Клиент 1 дарит бонус клиенту 2, а клиент 2 в ту же секунду — клиенту 1. Каждая транзакция сначала списывает у «своего», потом начисляет «чужому».

ШагОкно AОкно B
1BEGIN;
UPDATE bonus_wallet SET balance = balance - 1 WHERE customer_id = 1;
2BEGIN;
UPDATE bonus_wallet SET balance = balance - 1 WHERE customer_id = 2;
3UPDATE bonus_wallet SET balance = balance + 1 WHERE customer_id = 2; — висит, строку 2 держит B
4UPDATE bonus_wallet SET balance = balance + 1 WHERE customer_id = 1; — висит, строку 1 держит A

A ждёт B, B ждёт A — сами они никогда не разойдутся. PostgreSQL раз в секунду проверяет такие циклы и «убивает» одну из транзакций. Вторая продолжает работу. Выполните ROLLBACK; в обоих окнах. Лекарство — всегда блокировать строки в одном порядке, например по возрастанию id: сначала кошелёк с меньшим номером, потом с большим, кто бы ни был отправителем. А приложение должно уметь повторить транзакцию, если поймало deadlock detected.

→
УРОВНИ ИЗОЛЯЦИИ — ОДНОЙ СТРОКОЙ

Всё, что мы видели, — поведение уровня по умолчанию READ COMMITTED: каждая команда видит то, что зафиксировано к её началу. Есть уровни строже: REPEATABLE READ (вся транзакция видит один «снимок» базы) и SERIALIZABLE (база гарантирует результат, как если бы транзакции шли по очереди, и сама отменяет те, что мешают друг другу). Включаются так: BEGIN ISOLATION LEVEL SERIALIZABLE;. Для начала достаточно знать, что они есть.
