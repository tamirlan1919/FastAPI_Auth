NoSQL и MongoDB

На прошлом уроке мы построили в auth-api реляционную схему: users, posts, profiles, tags, связи через внешние ключи и миграции через Alembic. Сегодня посмотрим на данные с другой стороны — документоориентированная база MongoDB, где нет таблиц, JOIN-ов и миграций схемы, зато есть гибкие JSON-документы, вложенность и горизонтальное масштабирование. Разберём, когда это лучше SQL, а когда хуже, и добавим в проект настоящий модуль на MongoDB.

ЧТО РАЗБЕРЁМ

  • NoSQL: что это на самом деле, четыре типа баз и чем они отличаются от SQL.
  • Модель MongoDB: документ, коллекция, BSON, устройство ObjectId.
  • Моделирование: когда вкладывать данные (embedding), а когда ссылаться (referencing) — главный навык в NoSQL.
  • Async-подключение к FastAPI: драйвер, жизненный цикл клиента, зависимости, Pydantic и _id.
  • CRUD, операторы, индексы, транзакции, explain, агрегации — на живом модуле «Задачи» в нашем проекте.
i

Что строим. В auth-api пользователи, авторизация, посты и теги остаются в SQL (SQLAlchemy + Alembic). Рядом появляется модуль «Задачи» (todos) на MongoDB: каждая задача принадлежит текущему пользователю (по JWT из урока 4), содержит вложенный чек-лист, теги, приоритет, а все важные события пишутся в журнал activity. Слои те же: api · repositories · db · shemas · core.

Часть 1 · NoSQL и модель данных

01 · Что такое NoSQL

теория~10 мин

NoSQL — это не «анти-SQL», а «Not Only SQL», «не только SQL». Общее название для баз данных, которые хранят данные не в виде связанных таблиц со строгой схемой. Термин появился в конце 2000-х, когда компании вроде Google, Amazon и Facebook упёрлись в ограничения одной большой реляционной БД: данных и запросов стало столько, что один сервер — даже очень мощный — перестал справляться.

Три ключевых отличия от SQL

 SQL (PostgreSQL, SQLite)NoSQL (MongoDB)
Схемастрогая: таблица с фиксированными колонками; новое поле → ALTER TABLE → миграция Alembicгибкая: документы в одной коллекции могут иметь разные поля; новое поле — просто начинаем его писать
Модель данныхтаблицы и строки, связи через FK, данные нормализованыдокументы (JSON/BSON), пары ключ-значение, графы, колонки; данные часто денормализованы
Масштабированиеобычно вертикальное: мощнее серверизначально проектировалось под горизонтальное: больше серверов
 
Вертикальное (scale up)            Горизонтальное (scale out, sharding)
┌──────────┐      ┌────────────┐      ┌──────┐   ┌──────┐   ┌──────┐
│ 4 CPU    │ ───▶ │ 64 CPU     │      │ шард │   │ шард │   │ шард │
│ 16 GB    │      │ 512 GB     │      │ A–H  │   │ I–P  │   │ Q–Z  │
└──────────┘      └────────────┘      └──────┘   └──────┘   └──────┘
 упирается в потолок железа и цены     данные разрезаны по ключу,
                                       нужен ещё — добавили сервер
◆
ПОЧЕМУ NoSQL ПРОЩЕ МАСШТАБИРОВАТЬ

Горизонтальное масштабирование означает: разрезать данные на части (шарды) и разложить по разным серверам. Для SQL это больно: JOIN между таблицами на разных серверах и транзакция через несколько машин — очень дорогие операции. MongoDB изначально поощряет хранить всё, что читается вместе, в одном документе. Документ целиком живёт на одном шарде, поэтому большинство запросов вообще не требуют общения серверов между собой. Плата за это — денормализация и меньше гарантий «из коробки», чем у SQL.

Четыре типа NoSQL-баз

ТипКак хранитПримерТипичная задача

Колоночные (wide-column)строки с динамическим набором колонок, оптимизация под записьCassandraогромные потоки записей: метрики, IoT, логи

Репликация: replica set

Помимо шардирования, у MongoDB есть репликация: несколько серверов хранят одинаковые копии данных. Один — primary, принимает запись; остальные — secondary, повторяют его операции из журнала oplog. Упал primary — оставшиеся за секунды выбирают нового. Такая группа называется replica set.

               запись
   FastAPI ──────────────▶ ┌─────────┐
                           │ PRIMARY │──oplog──┐
                           └─────────┘         │
                                ▲              ▼
                      выборы    │       ┌────────────┐   ┌────────────┐
                      при сбое  └────── │ secondary  │   │ secondary  │
                                        └────────────┘   └────────────┘
i

Запомните слово replica set — оно понадобится в блоке про транзакции: мультидокументные транзакции в MongoDB работают только на replica set (или шардированном кластере). Поэтому даже локально мы сразу запустим MongoDB как replica set из одного узла.

02 · SQL или NoSQL: как выбирать

теория~8 мин

Нет «лучшей» базы — есть подходящая под форму данных и способ доступа к ним. Задавайте себе вопросы не «что модно», а «как я буду читать и писать эти данные».

MongoDB хорош, когда

  • Структура часто меняется или неоднородна. Товары в магазине: у ноутбука — «диагональ, RAM», у кроссовок — «размер, материал». В SQL это либо 100 nullable-колонок, либо сложная схема EAV; в Mongo — просто разные поля в документах.
  • Данные иерархичны и читаются целиком. Заказ с позициями, задача с чек-листом, статья с блоками — один документ, один запрос, без JOIN.
  • Много записи и нужна горизонтальная масштабируемость. Логи, события, аналитика, IoT.
  • Быстрое прототипирование (MVP). Нет миграций на каждое новое поле.

SQL лучше, когда

  • Много связей и запросов «через» них: отчёты с JOIN по 5 таблицам, сложные фильтры по связанным сущностям.
  • Критична строгая целостность: деньги, остатки на складе, бронирования. FK, CHECK, UNIQUE и транзакции в SQL — проверенная классика.
  • Данные стабильно структурированы: пользователи, роли, права.
!

Частый миф: «в MongoDB нет транзакций и целостности». Это устарело. Операция над одним документом в MongoDB атомарна всегда, а с версии 4.0 есть мультидокументные ACID-транзакции. Другое дело, что они дороже, чем в SQL, и хорошая схема в Mongo старается в них не нуждаться. Об этом — в блоке 12.

Решение для auth-api: polyglot persistence

В реальных системах часто используют несколько баз сразу, каждую для своей задачи — это называется polyglot persistence. Так поступим и мы:

ДанныеГде хранимПочему
users, роли, паролиSQLуникальность email/username, связи с posts/profiles, строгая схема, Alembic
posts, tags, profilesSQLмного-ко-многим и запросы по связям — сильная сторона SQL (урок 6)
todos (задачи)MongoDBвложенный чек-лист читается вместе с задачей, поля задач будут эволюционировать
activity (журнал событий)MongoDBмного записей, разная структура событий, автоудаление старых записей (TTL-индекс)
◆
ЧЕСТНО О ВЫБОРЕ

Задачи с чек-листом прекрасно легли бы и в PostgreSQL (отдельная таблица или колонка JSONB). Мы берём MongoDB, потому что на этом модуле удобно показать все ключевые приёмы документной базы. В рабочем проекте добавлять вторую БД стоит только когда выигрыш перевешивает цену: ещё один сервис в инфраструктуре, бэкапы, мониторинг и отсутствие общей транзакции между SQL и Mongo. Умение объяснить этот компромисс на собеседовании ценнее, чем знание синтаксиса.

Обратите внимание на связь между базами: задача хранит owner_id — id пользователя из SQL. Внешнего ключа между двумя разными базами быть не может, поэтому целостность здесь обеспечивает приложение: мы берём owner_id только из проверенного JWT, а не из тела запроса.

Как выглядит наша задача

Всё, что в SQL потребовало бы двух таблиц (todos + checklist_items с FK) и JOIN-а, здесь лежит в одном документе и читается одним запросом.

BSON — почему не просто JSON

Внутри MongoDB хранит документы в формате BSON (Binary JSON). Он похож на JSON, но бинарный и с более богатым набором типов:

Тип BSONВ PythonЗачем
ObjectIdbson.ObjectIdидентификатор документа (в JSON такого типа нет!)
Datedatetimeнастоящая дата (в JSON даты — просто строки); нужна для сортировки и TTL
Int32 / Int64 / Doubleint / floatв JSON есть только «number»
Decimal128bson.Decimal128точные деньги без ошибок float
Binarybytesбинарные данные, UUID
◆
ПОЧЕМУ ЭТО ВАЖНО ДЛЯ FastAPI

FastAPI отдаёт клиенту JSON, а в JSON нет ни ObjectId, ни Date. Значит, на границе «БД → API» мы обязаны преобразовать ObjectId в строку, а datetime — в ISO-строку. Даты Pydantic сериализует сам, а вот ObjectId — нет: если вернуть «сырой» документ, получите ошибку сериализации. Решаем это в блоке 07.

Анатомия ObjectId

ObjectId — 12 байт, которые генерирует драйвер на стороне приложения, а не сервер БД:

   6710a3f2   c8e1d2a3b4   c5d6e7
   └───┬──┘   └────┬───┘   └──┬─┘
   4 байта      5 байт       3 байта
   время        случайное    счётчик
   (секунды)    (на процесс)  (растёт)
  • Уникален без обращения к БД. Тысячи серверов приложения генерируют id параллельно и не конфликтуют — ключевое свойство для горизонтального масштабирования. Автоинкремент 1, 2, 3 из SQL так не умеет: ему нужен единый счётчик.
  • Примерно упорядочен по времени: сортировка по _id ≈ сортировка по времени создания. А ObjectId(...).generation_time вернёт дату создания.
  • Не секретен. По id видно время создания, поэтому id — не замена проверке прав. Мы всегда фильтруем ещё и по owner_id.

Важные ограничения

  • Максимальный размер документа — 16 МБ. Это главная причина не вкладывать в документ бесконечно растущие списки.
  • _id нельзя изменить после вставки.
  • Коллекции и базы создаются лениво: db["todos"] в Python ничего не создаёт — коллекция появится при первой вставке или создании индекса. Опечатка в имени коллекции не вызовет ошибку — вы просто запишете данные в новую коллекцию. Поэтому имена коллекций держим в одном месте (в репозитории).

04 · Моделирование: embedding vs referencing

теория~10 мин

В SQL правила проектирования одни: нормализуй, связывай через FK. В MongoDB главный вопрос другой: какие данные читаются вместе? У нас есть два инструмента.

 Embedding (вложение)Referencing (ссылка)
Каксвязанные данные лежат внутри документадокумент хранит id другого документа
Чтениеодин запрос, без JOINдва запроса или $lookup
Атомарностьизменение одного документа атомарно всегдадля нескольких документов — транзакция
Ростограничен 16 МБ на документне ограничен
Дублированиеесли данные общие — копии в разных документаххранится один раз

Правило большого пальца

  1. «Что читается вместе — хранится вместе». Чек-лист всегда показывают вместе с задачей → вкладываем.
  2. Один-к-нескольким (адреса пользователя, пункты чек-листа) → вкладываем массив.
  3. Один-к-очень-многим (события пользователя за годы, комментарии к популярному посту) → отдельная коллекция, ребёнок хранит ссылку на родителя (user_id). Иначе массив будет расти бесконечно и упрётся в 16 МБ.
  4. Данные живут сами по себе и нужны в разных местах (пользователь) → ссылка.

Тот же пример из урока 6 — глазами MongoDB

В SQL у нас были users, posts, tags и связующая post_tags. В Mongo пост мог бы выглядеть так:

  • Many-to-many исчезло: теги — просто массив строк. Поиск «все посты с тегом python» — find({"tags": "python"}), а индекс по массиву MongoDB строит сам (multikey-индекс).
  • Автор скопирован в пост. Список постов показываем без второго запроса. Но если alice сменит username — придётся обновить его во всех её постах (update_many). Это и есть цена денормализации: быстрое чтение в обмен на более сложное обновление. Оправдано, когда данные читают в разы чаще, чем меняют.
◆
НАШИ РЕШЕНИЯ ДЛЯ TODOS

Чек-лист → embedding: всегда читается с задачей, пунктов немного (ограничим 50), а добавление/отметка пункта — атомарная операция над одним документом без транзакций. Владелец → referencing (owner_id): пользователь живёт в другой базе. Журнал activity → отдельная коллекция: событий у пользователя может быть сотни тысяч, вкладывать их в документ пользователя или задачи нельзя.

!

Если вы постоянно пишете $lookup (аналог JOIN) между коллекциями — это сигнал, что либо модель спроектирована «по-SQL-ному», либо данные действительно реляционные и им место в SQL. MongoDB проектируют от запросов, а не от сущностей.

05 · Запуск MongoDB и mongosh

практика~8 мин

Варианты установки: Docker (наш выбор — одна команда, ничего не мусорит в системе), MongoDB Atlas (облако, есть бесплатный кластер — удобно для продакшена и деплоя) или локальная установка MongoDB Community Server.

Разберём каждую часть

  • -p 27017:27017 — стандартный порт MongoDB, пробрасываем наружу, чтобы FastAPI на хосте до него достучался.
  • -v auth_mongo_data:/data/db — именованный том. Без него при удалении контейнера пропадут все данные.
  • --replSet rs0 — сервер стартует как участник replica set с именем rs0. Без этого флага транзакции работать не будут.
  • --bind_ip_all — слушать все интерфейсы внутри контейнера (иначе подключиться снаружи не получится).
  • rs.initiate(...) — «собрать» replica set. Пока его не выполнить, узел не станет PRIMARY и не примет запись.
◆
ПОЧЕМУ REPLICA SET ДАЖЕ ЛОКАЛЬНО

Транзакции в MongoDB построены на механизме репликации (oplog). На одиночном сервере (standalone) попытка начать транзакцию упадёт с ошибкой Transaction numbers are only allowed on a replica set member or mongos. Чтобы dev-окружение вело себя как прод (где всегда replica set), запускаем replica set из одного узла. Ресурсов это не добавляет.

Строка подключения

Формат: mongodb://[user:password@]host[:port]/[database][?опции]

  • локально у нас: mongodb://localhost:27017/?directConnection=true
  • с авторизацией: mongodb://user:password@localhost:27017/?authSource=admin
  • Atlas: mongodb+srv://user:password@cluster0.xxxxx.mongodb.net — строку выдаёт интерфейс Atlas
i

directConnection=true говорит драйверу: «подключайся прямо к этому узлу, не пытайся обнаружить остальных участников replica set». Для локального однонодового кластера это убирает целый класс проблем с именами хостов. В продакшене с настоящим кластером эту опцию не ставят.

06 · Драйвер и подключение (lifespan)

практика~12 мин

Какой драйвер: Motor или PyMongo Async

Долгое время стандартом для async-работы с MongoDB был Motor — именно его вы встретите в большинстве статей и курсов. Но в 2025 году MongoDB выпустила нативный асинхронный API прямо в официальном драйвере PyMongo (AsyncMongoClient, PyMongo 4.13+) и объявила Motor устаревшим (deprecated) — он получает только критические исправления, а новые проекты рекомендуется писать на PyMongo Async.

◆
ПОЧЕМУ ПОЯВИЛАСЬ ЗАМЕНА

Motor был «обёрткой»: под капотом он запускал синхронный PyMongo в пуле потоков и превращал результаты в awaitable-объекты. Это работало, но добавляло накладные расходы на потоки. AsyncMongoClient написан на asyncio нативно — без пула потоков, быстрее и с меньшей задержкой. API при этом почти идентичен, поэтому всё, что вы знаете про Motor, переносится один в один.

Если в вашем курсе/проекте уже Motor — код этого урока переносится заменой импорта и трёх строк из таблицы выше. Различия подробно описаны в официальном руководстве «Migrate to PyMongo Async» в документации MongoDB.

Шаг 1. Настройки

pydantic-settings сопоставляет переменные окружения с полями без учёта регистра: MONGO_URL → mongo_url. Значения по умолчанию позволяют запустить проект локально даже без правки .env, а на сервере URL с паролем приходит из окружения и в репозиторий не попадает.

Шаг 2. Модуль подключения

Почему каждый параметр именно такой

  • Один клиент на всё приложение. AsyncMongoClient — это не одно соединение, а пул соединений (по умолчанию до 100) плюс фоновый мониторинг кластера. Создавать клиента на каждый запрос — грубая ошибка: каждый раз заново TCP-рукопожатие, аутентификация и утечка ресурсов.
  • tz_aware=True. MongoDB хранит даты в UTC, но по умолчанию PyMongo возвращает «наивные» datetime без часового пояса. Сравнение наивной даты с datetime.now(timezone.utc) падает с TypeError, а клиент API получает дату без Z и может интерпретировать её как локальную. С tz_aware=True всё однозначно.
  • serverSelectionTimeoutMS=5000. Если Mongo не запущена, без этой опции приложение будет «висеть» 30 секунд на первом запросе. Быстрый и понятный сбой лучше.
  • request.app.state — место для общих объектов приложения. Зависимость берёт базу оттуда, а не из глобальной переменной модуля — в тестах легко подменить через app.dependency_overrides.

Шаг 3. Жизненный цикл: lifespan

Сейчас в main.py используется @app.on_event("startup"). Этот механизм в FastAPI устарел; современный способ — lifespan: одна функция-контекстный менеджер, где код до yield выполняется при старте, а после — при остановке.

◆
ПОЧЕМУ LIFESPAN, А НЕ on_event

Ресурс, открытый при старте, должен быть закрыт при остановке. С on_event это два несвязанных обработчика, и клиента приходится прятать в глобальную переменную, чтобы передать из одного в другой. В lifespan открытие и закрытие — в одной функции, в одной области видимости, как у async with. А ping при старте превращает «упало на первом пользовательском запросе через 5 минут» в «не стартовало, потому что Mongo недоступна» — такие ошибки ловятся сразу при деплое.

!

Если в main.py ещё остался Base.metadata.create_all — после урока 6 схемой SQL управляет Alembic (alembic upgrade head), и create_all из старта лучше убрать. А вот индексы MongoDB создаём именно при старте: у Mongo нет Alembic, и create_index идемпотентен (повторный вызов с тем же описанием ничего не делает).

Шаг 4. Зависимости

Ровно тот же паттерн, что у UserRepoDep / PostRepoDep: роутер не знает, откуда берётся база, он получает готовый репозиторий. Разница лишь в источнике: SQL-репозиторий получает AsyncSession, Mongo-репозиторий — AsyncDatabase.

Проверка: uvicorn app.main:app --reload стартует без ошибок. Остановите контейнер (docker stop auth-mongo) и перезапустите приложение — оно должно упасть на старте через ~5 секунд с ServerSelectionTimeoutError. Запустите контейнер обратно.

07 · Pydantic-схемы и ObjectId

практика~8 мин

Задача схем — та же, что в уроке 3: разделить что приходит (Create/Update) и что уходит (Out). Новое — проблема _id: в базе это ObjectId в поле _id, а клиенту API нужен "id": "6710a3f2..." строкой.

Разберём ключевые детали

  • PyObjectId = Annotated[str, BeforeValidator(str)] — «строка, но перед проверкой прогони значение через str()». Из базы приходит ObjectId("6710..."), валидатор превращает его в "6710...", и дальше это обычная строка, которую FastAPI легко сериализует в JSON.
  • Field(validation_alias="_id") — при чтении данных бери значение из ключа _id, а при выдаче используй имя поля id. Документ из Mongo читается как есть, а клиент получает привычный "id".
  • Нет owner_id и is_completed во входных схемах. Владельца берём из JWT, а выполнение задачи — отдельное действие с транзакцией (блок 12). Если бы owner_id был в TodoCreate, любой мог бы создать задачу от чужого имени.
  • TodoOut(TodoBrief) — наследование схем: полная форма = короткая + дополнительные поля.
!

Во многих примерах пишут id: str = Field(alias="_id"). Ловушка: alias работает в обе стороны, а FastAPI отдаёт ответ по алиасам (response_model_by_alias=True по умолчанию). В итоге в JSON вы получите "_id", а не "id", и эту же схему можно случайно принимать на вход вместе с _id от клиента. validation_alias влияет только на чтение — то, что нужно.

Гибкая схема ≠ отсутствие схемы

MongoDB не проверяет структуру документов — значит, проверять должны мы. Схема никуда не делась: она переехала из базы в код — в Pydantic-модели. Всё, что попадает в базу, проходит через TodoCreate/TodoUpdate; всё, что уходит клиенту, — через TodoOut.

◆
А КАК ЖЕ МИГРАЦИИ?

Alembic в Mongo не нужен, но эволюция данных никуда не исчезла. Допустим, через месяц мы добавили поле priority. Старые документы его не содержат. Два пути: (1) значение по умолчанию в схеме (priority: int = 2 в TodoBrief) — старые документы читаются без ошибок; (2) скрипт-«миграция данных», который проставит поле всем старым документам:

await db.todos.update_many({"priority": {"$exists": False}}, {"$set": {"priority": 2}})

Обычно делают оба: дефолт — чтобы не упасть сразу, скрипт — чтобы данные были однородными и по полю работали индексы и фильтры.

08 · CRUD: репозиторий задач

практика~14 мин

Вся работа с MongoDB — в репозитории, как и с SQL. Роутер ничего не знает про $set и ObjectId-фильтры.

Разбор по методам

create

  • insert_one возвращает InsertOneResult, в котором inserted_id — сгенерированный ObjectId. (PyMongo к тому же дописывает _id прямо в переданный словарь; явное присваивание делает код понятнее.)
  • Служебные поля (owner_id, is_completed, даты) выставляет сервер, а не клиент — так мы гарантируем однородность документов.
  • DuplicateKeyError возникнет из-за уникального индекса (owner_id, title) из блока 11. Переводим ошибку драйвера в доменное исключение — роутеру незачем знать про PyMongo.

get

Фильтр всегда содержит owner_id. Даже если злоумышленник знает _id чужой задачи, find_one вернёт None, и он получит 404. Мы не проверяем владельца отдельным if после загрузки — мы вообще не загружаем чужое.

list_for_owner

  • find() не выполняет запрос и не требует await — он возвращает курсор, к которому мы цепочкой добавляем sort / skip / limit. Запрос уходит в БД только при чтении: await cursor.to_list(...) или async for doc in cursor.
  • to_list(length=limit) — защита от загрузки миллиона документов в память.
  • count_documents(filt) — общее количество под фильтр, для пагинации на фронтенде.
  • re.escape(q) — экранирование пользовательского ввода. Без него строка .* или специально составленная регулярка превратится в «найди всё» или в ReDoS-атаку, которая загрузит сервер БД.

update

  • model_dump(exclude_unset=True) — только реально присланные поля. Без этого PATCH {"priority": 1} затёр бы title значением None.
  • $set — меняет только указанные поля. Если передать в update_one словарь без оператора, PyMongo выдаст ошибку; а replace_one заменил бы документ целиком — потеряли бы чек-лист.
  • find_one_and_update(..., return_document=ReturnDocument.AFTER) — найти, обновить и вернуть новую версию документа одной атомарной операцией. Альтернатива update_one + find_one — два запроса, и между ними документ мог измениться.

delete

delete_one возвращает DeleteResult; deleted_count == 0 означает «не нашли» — либо нет такой задачи, либо она чужая. Для клиента оба случая — 404.

!

NoSQL-инъекции. В MongoDB фильтр — это словарь, и если подставить в него «сырой» JSON от клиента, можно получить {"owner_id": {"$ne": null}} — «все задачи всех пользователей». Защита: никогда не передавайте в фильтр необработанные данные запроса; все значения проходят через типизированные параметры и Pydantic (int, bool, str), которые не пропустят словарь с операторами.

→

Шпаргалка «SQL → MongoDB»: INSERT → insert_one/insert_many; SELECT ... WHERE → find(filter); ORDER BY / LIMIT / OFFSET → .sort() / .limit() / .skip(); COUNT(*) → count_documents; UPDATE ... SET → update_one/update_many + $set; DELETE → delete_one/delete_many; GROUP BY → aggregate + $group.

практика~6 мин

Что здесь важно

  • parse_todo_id как зависимость. FastAPI видит параметр todo_id: str и берёт его из пути /{todo_id}. Строка "abc" — невалидный ObjectId: без проверки ObjectId("abc") бросит InvalidId → 500. Мы отвечаем 404: с точки зрения клиента такой задачи просто не существует.

практика~8 мин

◆
ПОЧЕМУ ОПЕРАТОРЫ, А НЕ «ПРОЧИТАЛ-ИЗМЕНИЛ-ЗАПИСАЛ»

Наивный путь: прочитать документ в Python, добавить пункт в список, записать документ обратно. Если два запроса сделают это одновременно, второй перезапишет изменения первого — потерянное обновление (lost update). Операторы $push, $pull, $inc выполняются на сервере атомарно над одним документом: два параллельных $push добавят оба пункта. Это главный выигрыш embedding: изменения вложенных данных атомарны без транзакций.

Практика: чек-лист внутри задачи

Разберём хитрые места

  • "_id": ObjectId() у пункта. Вложенные документы не получают _id автоматически. Мы даём его сами, чтобы адресовать конкретный пункт в URL: /todos/{id}/checklist/{item_id}. Номер в массиве не подходит: после удаления пункта номера сдвигаются.
  • "checklist.49": {"$exists": False} — «у массива нет элемента с индексом 49», то есть пунктов меньше 50. Проверка лимита прямо в фильтре атомарна: в отличие от if len(...) < 50 в Python, параллельные запросы не проскочат лимит.
  • "checklist._id": item_id в фильтре — точечная нотация: ищем документ, у которого какой-то элемент массива имеет такой _id.
  • "checklist.$.done" — $ подставляет позицию того элемента, что совпал в фильтре. Обновляем один пункт, не трогая остальные.
  • $pull удаляет из массива элементы под условие {"_id": item_id}.
Проверка: добавляем к задаче три пункта, отмечаем второй как done: true, удаляем первый. В ответе каждый раз — актуальная задача с чек-листом, у пунктов свои строковые id. В mongosh видно, что всё это — один документ.

11 · Индексы

практика~12 мин

Без индекса MongoDB, чтобы выполнить find({"owner_id": 1}), перебирает каждый документ коллекции — это называется COLLSCAN (full collection scan). На 100 документах незаметно, на 10 миллионах — секунды на запрос и загруженный сервер. Индекс — отсортированная структура (B-дерево) «значение поля → где лежит документ», по которой поиск идёт за логарифмическое время — IXSCAN.

COLLSCAN: читаем всё                 IXSCAN: идём по индексу
┌───┬───┬───┬───┬───┬───┬───┐       owner_id
│ 7 │ 1 │ 3 │ 1 │ 9 │ 1 │ 2 │         ┌─ 1 ──▶ док, док, док   ← берём только их
└───┴───┴───┴───┴───┴───┴───┘         ├─ 2 ──▶ док
  проверили 7 из 7, нашли 3           ├─ 3 ──▶ док
                                      └─ ...  проверили 3, нашли 3
◆
ЦЕНА ИНДЕКСА

Индекс не бесплатен: он занимает память (рабочий набор индексов должен помещаться в RAM) и замедляет запись — каждый insert/update обновляет все индексы коллекции. Поэтому индексы создают не «на всякий случай», а под конкретные запросы, которые реально выполняет приложение. MongoDB автоматически создаёт только один индекс — по _id.

Разберём каждый вид индекса

Составной индекс и правило ESR

Индекс (owner_id, created_at desc) — составной: документы упорядочены сначала по owner_id, внутри — по дате. Запрос «задачи пользователя 1, новые сверху» читает готовый отсортированный кусок индекса — сортировка в памяти не нужна. Порядок полей в составном индексе выбирают по правилу ESR:

  1. Equality — сначала поля, которые сравниваются на равенство (owner_id = 1, tags = "work");
  2. Sort — затем поля сортировки (created_at desc);
  3. Range — в конце поля с диапазонами ($gte, $lt, $regex).
◆
ПОЧЕМУ ПОРЯДОК ВАЖЕН

Составной индекс похож на телефонный справочник, отсортированный по фамилии, потом по имени. Найти «Иванов Пётр» — мгновенно. Найти всех «Петров» без фамилии — придётся читать весь справочник. Поэтому индекс (owner_id, created_at) помогает запросу по owner_id (префикс индекса), но не помогает запросу только по created_at. И наш индекс (owner_id, created_at) делает отдельный индекс по одному owner_id лишним.

Multikey-индекс

tags — массив. Индексируя такое поле, MongoDB создаёт запись в индексе для каждого элемента массива. Поэтому find({"owner_id": 1, "tags": "work"}) идёт по индексу, хотя "work" — лишь один из элементов. Создаётся так же, как обычный индекс, MongoDB сама понимает, что поле — массив.

Unique-индекс

unique=True на (owner_id, title) — бизнес-правило «у одного пользователя не может быть двух задач с одинаковым заголовком», которое гарантирует сама база. Проверка в Python (find_one перед insert) не спасает от гонки: два параллельных запроса оба увидят «дубля нет» и оба вставят. Уникальный индекс отклонит второй с DuplicateKeyError — мы превращаем его в 409.

i

Уникальность по умолчанию учитывает регистр: «Купить хлеб» и «купить хлеб» — разные значения. Если нужно без учёта регистра — индекс создают с параметром collation={"locale": "ru", "strength": 2}, и тот же collation указывают в запросах.

TTL-индекс

expireAfterSeconds превращает обычный индекс по дате в «таймер самоуничтожения»: фоновый процесс MongoDB примерно раз в минуту удаляет документы, у которых created_at старше 90 дней. Журнал событий не растёт бесконечно, и нам не нужен cron-скрипт для очистки. Условие: поле должно быть типа Date (поэтому мы храним datetime, а не строку).

!

В старых примерах (включая материалы про Motor) встречается create_index(..., background=True). Начиная с MongoDB 4.2 этот параметр игнорируется: сервер всегда строит индекс оптимизированным способом, блокируя коллекцию лишь в начале и в конце. Ещё одна ловушка: если вызвать create_index с тем же набором полей, но другими опциями (например, добавить unique), получите ошибку IndexOptionsConflict — старый индекс надо сначала удалить (drop_index).

Проверка: перезапускаем приложение, в mongosh db.todos.getIndexes() — видим _id_ и три наших индекса. Создаём две задачи с одинаковым title → вторая получает 409. Индексы мы ещё увидим в работе через explain в блоке 13.

12 · Транзакции

практика~10 мин

Сценарий: пользователь отмечает задачу выполненной. Нужно сделать две записи в двух коллекциях: обновить задачу в todos и добавить событие в activity. Если первая прошла, а вторая упала (сеть, перезапуск сервера), журнал будет врать — задача выполнена, а события нет. Нужна атомарность: либо обе записи, либо ни одной.

Атомарность в MongoDB: два уровня

  • Один документ — любая операция атомарна всегда, даже если меняет десяток полей и вложенные массивы. Поэтому чек-листу (блок 10) транзакции не нужны.
  • Несколько документов / коллекций — нужна мультидокументная ACID-транзакция (с MongoDB 4.0 для replica set, с 4.2 — и для шардированных кластеров).
◆
ПОЧЕМУ В MONGO ТРАНЗАКЦИИ — ИСКЛЮЧЕНИЕ, А НЕ ПРАВИЛО

Транзакции в MongoDB полноценные, но дороже, чем одиночные операции: сервер держит снимок данных и блокировки на всё время транзакции, а по умолчанию транзакция дольше 60 секунд принудительно отменяется. Хорошая документная схема старается уложить то, что должно меняться атомарно, в один документ. Транзакция — инструмент для случаев, когда данные по-честному живут в разных коллекциях, как наша задача и журнал.

Разбор построчно

  • self.client.start_session() — сессия: «контекст», к которому сервер привязывает транзакцию. Для Motor здесь было бы async with await client.start_session().
  • session.with_transaction(txn) — запускает транзакцию, вызывает нашу функцию, коммитит при успехе и откатывает при исключении. Главное — он автоматически повторяет транзакцию при временных ошибках (TransientTransactionError, например при смене primary) и повторяет коммит при UnknownTransactionCommitResult. Писать эти повторы руками — источник багов.
  • session=session в каждой операции. Самая коварная ошибка: забыли передать сессию — операция выполнится мимо транзакции, сразу и навсегда, и не откатится при сбое. Никакой ошибки при этом не будет.
  • "is_completed": False в фильтре — условное обновление. Два параллельных «выполнить» не создадут два события: второй запрос не найдёт невыполненную задачу и вернёт None. Это идемпотентность на уровне базы.
  • Функция txn из-за повторов может выполниться несколько раз, поэтому внутри — только операции с БД, без отправки писем или вызовов внешних API.
i

Второй, «ручной» стиль: async with session.start_transaction(): ... (в PyMongo Async — async with await session.start_transaction():). Он коммитит при выходе из блока и откатывает при исключении, но не повторяет при временных ошибках. Для прикладного кода предпочитайте with_transaction.

!

Ограничения транзакций, которые важно помнить: работают только на replica set (на standalone — ошибка Transaction numbers are only allowed on a replica set member or mongos); держите их короткими (лимит по умолчанию 60 с); не создавайте внутри коллекции «на лету» — поэтому мы создаём индексы (а с ними и коллекции) при старте. И главное: транзакция MongoDB не охватывает SQL-базу. Атомарно изменить задачу в Mongo и пользователя в SQLite одной транзакцией нельзя — это задача уже распределённых систем (паттерны Outbox / Saga).

Проверка: POST /todos/{id}/complete → 200, is_completed: true, completed_at заполнен; в mongosh db.activity.find() — одно событие todo.completed. Повторный вызов → 409, второго события нет. Эксперимент на откат: временно добавьте raise RuntimeError("boom") сразу после insert_one в txn → 500, и при этом задача осталась невыполненной, а событие не записано. Уберите raise.

13 · Projection, explain, агрегации

практика~6 мин

Projection: берём только нужные поля

Мы уже применили её в list_for_owner: find(filt, {"description": 0, "checklist": 0}). Второй аргумент find — проекция: 0 — исключить поле, 1 — включить только перечисленные (смешивать нельзя, кроме _id). В списке задач описание и чек-лист не показываются — незачем гонять их по сети и разбирать в Python. На документах с большими вложенными массивами это экономит в разы. Поэтому и схема ответа у списка своя — TodoBrief.

explain: доказываем, что индекс работает

Индекс, которым база не пользуется, бесполезен. Проверяем на объёме: зальём 50 000 тестовых задач в отдельную коллекцию.

  • COLLSCAN / IXSCAN — стадии плана: полный перебор или поиск по индексу. Ищите их в winningPlan (стадия IXSCAN бывает вложена во FETCH).
  • totalDocsExamined против nReturned — главная метрика: сколько документов прочитали ради скольких вернули. Идеал — примерно равны. 50 000 прочитано ради 100 — запрос нужно индексировать.
  • Если в плане есть стадия SORT — сортировка идёт в памяти, индекс её не покрывает (вспоминаем ESR).
