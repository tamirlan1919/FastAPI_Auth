Docker Compose: весь стек одной командой

На прошлом уроке мы научились собирать образы: многоэтапный Dockerfile, nginx для фронтенда, ARG и ENV, USER. Но настоящее приложение — это не один контейнер, а несколько: фронтенд, API, база, кеш. Сегодня берём новый проект — QuickPoll, живой опрос «Какой фреймворк взять в новый проект?», и описываем все его части в одном файле compose.yaml. Запуск — одна команда docker compose up.

ЧТО СДЕЛАЕМ ЗА УРОК

  • Поднимем PostgreSQL и Redis из compose-файла и поймём, откуда берутся имена контейнеров, сетей и томов.
  • Подключим API по именам сервисов и увидим две настоящие ошибки старта: «база ещё не готова» и «таблиц ещё нет».
  • Сделаем миграции отдельным сервисом, который один раз создаёт таблицы и завершается, а API ждёт его успеха. Заодно найдём ловушку со знаком $.
  • Вынесем пароль в .env и узнаем, почему смена пароля «ломает» уже созданную базу.
  • Добавим фронтенд: увидим CORS в браузере, починим прокси в nginx и разделим сети, чтобы фронтенд физически не мог достучаться до базы.
  • Сделаем режим разработки с горячей перезагрузкой и подключим Adminer через профили.
  • Запустим три копии API и докажем, почему состояние (лимит «один голос в 10 секунд») должно жить в Redis, а не в памяти процесса: с памятью один человек проголосовал три раза.

✦
АНАЛОГИЯ: ПАРТИТУРА

Dockerfile — ноты для одного музыканта: как собрать один образ. compose.yaml — партитура оркестра: кто играет, кто вступает после кого, кто кого слышит. Вы не раздаёте указания каждому — кладёте партитуру и говорите «играем»: docker compose up.

★
ФРОНТЕНДЕРАМ ЭТО ЗНАКОМО

Похоже на package.json: зависимости и скрипты описаны в файле, и любой запускает проект одной командой. Разница: Compose описывает желаемое состояние («должны работать вот такие сервисы вот с такими настройками»). Повторный up не перезапускает всё подряд — Compose меняет только то, что отличается от описания.

YAML ЗА МИНУТУ

Вложенность — пробелами, обычно по два, табы запрещены. ключ: значение — словарь, - элемент — список, [a, b] — короткая запись списка. Порты пишите в кавычках ("8080:80"): YAML 1.1 читает некоторые «числа с двоеточием» как время. Ошибётесь в отступе — Compose назовёт строку.

◆
ПОЧЕМУ НЕ docker-entrypoint-initdb.d

Официальный образ Postgres умеет сам выполнить SQL-файлы из папки /docker-entrypoint-initdb.d (мы видели это в уроке 1). Но эти скрипты выполняются только на пустом томе — при первом запуске. Добавили завтра вторую миграцию 002_comments.sql — у всех, у кого база уже есть, она не выполнится. Поэтому миграции делают отдельным шагом, который запускается при каждом старте и сам решает, что уже сделано.

Сервис migrate: берём образ postgres:18 ради программы psql, прогоняем все файлы из папки и завершаемся. А api ждёт, когда он завершится успешно:

(Строки WARN у меня выглядят как time="…" level=warning msg="The \"f\" variable is not set…" — сократил.) Compose считает $f своей переменной, как ${DB_PASSWORD}, не находит её и подставляет пустоту — до того, как команда дойдёт до sh. Зато хорошо видно, что условие работает: миграция упала — API даже не запускался. Знак доллара для оболочки внутри контейнера удваиваем: $$f.

Последний вывод показательный: значения не поменялись — Compose не пересоздал ни базу, ни API. Только снова прогнал разовую миграцию. Это и есть «желаемое состояние».

!
ДВА РАЗНЫХ .env

.env рядом с compose.yaml — только для подстановки ${…} в сам файл; в контейнеры он сам по себе не попадает. env_file: .env у сервиса — передать в контейнер все переменные из файла. Методичка советует второе, но тогда каждый сервис получает всё подряд, включая чужие пароли. Мы перечисляем у каждого сервиса только нужное. И конечно: .env — в .gitignore, а в git — .env.example.

«Поменял пароль — всё сломалось»

POSTGRES_PASSWORD применяется только при первой инициализации тома. База уже создана со старым паролем, а все клиенты пришли с новым. Выходы: вернуть старый пароль; сменить его в самой базе (ALTER USER postgres PASSWORD '…'); или, если данные не нужны, docker compose down -v. Хорошо, что у нас миграция стоит «на входе»: сломанный стек не запустился наполовину.

06 · Фронтенд, CORS и две сети

live-coding~17 мин

Фронтенд в web/ устроен как films-web из прошлого урока: многоэтапный Dockerfile, Node собирает, nginx раздаёт, адрес API «запекается» через ARG VITE_API_URL. Первая попытка — адрес API, как мы привыкли на компьютере:

Страница пришла с localhost:8080, а запрос — на localhost:3000. Другой порт — другой origin, и браузер не отдаёт ответ странице, пока сервер явно не разрешит.

«Тогда напишу http://api:3000, как в методичке» — не сработает тоже: браузер ответит net::ERR_NAME_NOT_RESOLVED.

◆
ГДЕ ВЫПОЛНЯЕТСЯ КОД ФРОНТЕНДА

Контейнер web только отдаёт файлы. Выполняет JS браузер на вашем компьютере. Он не в сети Docker и имён сервисов не знает — ему доступно только то, что открыто через ports. Главная мысль блока: «внутри Docker» живут nginx, API, база и Redis, а браузер — всегда снаружи.

Решение: nginx проксирует /api

Пусть браузер ходит туда же, откуда пришла страница, — на /api/…, а nginx внутри сети передаёт запросы в api. Один origin — CORS не нужен. В Dockerfile уже стоит ARG VITE_API_URL=/api, так что args в compose можно убрать.

РАЗБОР

X-Forwarded-Forпередать IP браузераиначе API увидит адрес nginx у всех — и лимит «один голос в 10 секунд» станет общим на всех пользователей

Две сети: фронтенд не должен видеть базу

Пока все сервисы в одной сети default. Значит, контейнер web (а это nginx, который смотрит в интернет) может открыть соединение прямо к Postgres. Если в nginx найдут уязвимость — до базы рукой подать. Разделим:

ГЛАВНЫЙ ВЫВОД: КОНТЕЙНЕР ПРИЛОЖЕНИЯ БЕЗ СОСТОЯНИЯ

Всё, что должно пережить перезапуск или быть общим для копий — сессии, лимиты, загруженные файлы, кеш, — живёт вне контейнера приложения: в базе, Redis, томе, S3. Тогда копий можно запустить сколько угодно, а любую — убить и пересоздать. Это одно из правил «12 Factor App», которое упоминает методичка.

!
ДВЕ ЛОВУШКИ МАСШТАБИРОВАНИЯ

1. nginx узнаёт адреса api один раз — при старте. После пересоздания или добавления копий у них новые IP, и nginx продолжит слать запросы на старые (или не увидит новые). Поэтому после --scale выполняем docker compose restart web. 2. Обычный up -d без --scale вернёт одну копию: Compose приводит всё к описанному в файле. Нужно постоянно три — пишите в сервисе deploy: replicas: 3.

Чек-лист «не работает»

  1. docker compose ps -a — кто не Up? Exited (1), Restarting, (unhealthy), Created (не дождался зависимости).
  2. docker compose logs --tail 50 сервис — первая ошибка обычно говорит всё. Не забудьте логи migrate.
  3. Не видит другой сервис → docker compose exec api getent hosts db. Пусто — опечатка в имени или сервисы в разных сетях.
  4. Настройки не те → docker compose config.
  5. Старый код → docker compose up -d --build.

  3. Сброс голосов. Сервис reset в профиле tools, который выполняет TRUNCATE votes и удаляет ключ results в Redis. Запуск: docker compose run --rm reset. В каких сетях он должен быть?
  4. Свой проект. Возьмите свой фронтенд (или PizzaHub) и опишите в Compose: фронтенд + любой готовый API-мок (например, json-server в контейнере Node) + прокси /api в nginx. Режим разработки — через override.
