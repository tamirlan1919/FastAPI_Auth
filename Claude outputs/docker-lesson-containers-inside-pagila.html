Docker: контейнеры изнутри

Весь блок SQL вы работали с базой Pagila, которую подняли одной командой docker compose up и, скорее всего, ни разу не задумались, что произошло. На вашем компьютере нет PostgreSQL, но база работает. Ни один SQL-файл вы не запускали руками, а в ней 1000 фильмов. Сегодня разберём эту «магию» по винтикам: соберём ту же Pagila своими руками одной командой docker run, сохраним данные в томе, упакуем в контейнер маленький Node.js-API к этой базе и соединим два контейнера в сеть.

ЧТО СДЕЛАЕМ ЗА УРОК

  • Разберёмся, чем контейнер отличается от виртуальной машины — и увидим, что контейнер занимает 652 КБ памяти и стартует за 0,24 с.
  • Заглянем внутрь Docker: CLI, демон, REST API (спросим демона через curl), реестр.
  • Поймём слои и «одноразовость» контейнера: куда пропадают файлы и почему.
  • Поднимем Postgres с Pagila одной командой и сохраним таблицу из урока про DDL в томе — она переживёт удаление контейнера.
  • Напишем Dockerfile для API films-api и запустим его рядом с базой в общей сети.

ПОЧЕМУ КИТ

Docker в переводе — «докер», портовый грузчик. До изобретения стандартного морского контейнера в 1950-х корабль грузили неделю: мешки, бочки, ящики разного размера. Потом всё стали класть в одинаковые железные коробки, которые одинаково грузит любой кран в любом порту. Docker сделал то же самое с программами: неважно, что внутри — Python, Node или Postgres, — запускается всё одной командой. А кит на логотипе везёт эти контейнеры на спине.

02 · Контейнер — это просто процесс

live~12 мин

Звучит как «маленький компьютер внутри компьютера», но на деле контейнер — обычный процесс вашей ОС, на который надели «шоры»: он видит только свои файлы, свои процессы и свою сеть. Проверим.

РАЗБОР
КодЧто значитЗачем так
docker runсоздать контейнер из образа и запустить егоесли образа нет локально, Docker сначала скачает его
--rmудалить контейнер, как только он завершитсядля одноразовых команд — чтобы не копился мусор
ubuntu:24.04образ ubuntu, тег (версия) 24.04без тега Docker возьмёт latest — это «какая-то последняя», не надо так
uname -rкоманда, которую выполнить внутривсё, что после имени образа, — команда для контейнера
!
НА MAC И WINDOWS БУДЕТ ПО-ДРУГОМУ

Контейнерам нужно ядро Linux. У macOS и Windows его нет, поэтому Docker Desktop тихо запускает маленькую Linux-виртуалку, и все контейнеры живут в ней. Вы увидите ядро вроде 6.10.14-linuxkit, отличное от uname -r на вашем Mac. На Windows для этого нужен режим WSL 2 — он включается в настройках Docker Desktop. На Linux-серверах, где работает прод, виртуалки нет: контейнеры — родные процессы.

Где этот процесс?

На Linux-хосте ps -ef | grep "sleep 3600" показывает тот же процесс №12295 — без всякого Docker. Внутри контейнера он считает себя первым и единственным. Это работа двух механизмов ядра Linux:

МеханизмЧто делаетЧто мы видели
namespaces (пространства имён)«шоры»: свой список процессов, своё имя хоста, своя файловая система, своя сетьPID 1 внутри, свой hostname
cgroups (контрольные группы)«ограничитель»: сколько памяти и процессора можно взятьdocker stats, флаги --memory 512m --cpus 1
→
КОНТЕЙНЕР ЖИВЁТ, ПОКА ЖИВЁТ ЕГО ПРОЦЕСС

echo привет отработал за миллисекунду — и контейнер завершился. sleep 3600 держит контейнер час. Postgres, nginx, Node-сервер работают «вечно» — и контейнер с ними. Частый вопрос новичков: «запустил контейнер, а он сразу остановился» — значит, главный процесс закончил работу или упал. Смотрите docker logs.

ДОСТУП К СОКЕТУ = ДОСТУП КО ВСЕМУ КОМПЬЮТЕРУ

Кто может отправлять запросы в docker.sock, тот может запустить контейнер с доступом к любым файлам хоста. Поэтому в интернете иногда встречается совет «примонтируйте сокет в контейнер» (-v /var/run/docker.sock:/var/run/docker.sock) — он даёт контейнеру права администратора. Так делают только для доверенных инструментов.

◆
ПОЧЕМУ ТАК УСТРОЕНО — И ПОЧЕМУ ЭТО ХОРОШО

Образ один и неизменный, поэтому 10 контейнеров Postgres не занимают 10 копий Postgres на диске — слои образа общие. А «одноразовость» контейнера — фича, а не баг: сломался — удалили и создали заново из того же образа, получили гарантированно чистое состояние. Но отсюда правило: всё, что нужно сохранить (данные базы, загруженные файлы), должно жить вне контейнера, в томе. Без тома база в контейнере потеряет данные при первом же пересоздании. Именно это мы и увидим после перерыва.

★
ФРОНТЕНДЕРАМ ЭТО ЗНАКОМО

Слои похожи на кеш node_modules в CI: если package-lock.json не менялся, зависимости не ставятся заново. Docker устроен так же: если слой не менялся, он берётся из кеша. В блоке 07 мы этим воспользуемся.

Начнём с самой короткой команды — и сразу ошибки:

Хорошая ошибка: образ сам говорит, чего ему не хватает. Настройки в контейнер передают через переменные окружения — как .env во фронтенд-проекте. Куда делась таблица?

Пересоздадим контейнер — как будто обновили образ или перезагрузили сервер с чистой установкой:

Таблицы нет. Но откуда два «тома» с длинными именами? Авторы образа postgres знают про одноразовость контейнеров и прописали в нём: «папку с данными храни в томе». Если том не указали, Docker создаёт анонимный том для каждого нового контейнера. Наши данные остались в первом томе, но новый контейнер получил второй, пустой. Старый том теперь — мусор на диске: у меня два таких тома заняли 80 МБ. Убрать: docker volume prune -a.

Две ошибки, которые вы точно встретите

Порт на компьютере может занять только один контейнер (или программа). Решение — другой внешний порт: -p 5434:5432. Внутренний порт менять не нужно: у каждого контейнера своя сеть, и 5432 внутри не конфликтует. Но если просто исправить порт и повторить команду, вы получите вторую ошибку:

Неудачный docker run успел создать контейнер (статус Created в docker ps -a), просто не смог его запустить. Имя занято. Сначала docker rm pg-two, потом повтор.

«Я ПОМЕНЯЛ SQL-ФАЙЛ, А БАЗА СТАРАЯ!»

Видите строку Skipping initialization? Скрипты из /docker-entrypoint-initdb.d выполняются только при пустом томе. Если в томе уже есть база, их пропускают — иначе каждый перезапуск затирал бы ваши данные. Чтобы инициализировать заново, удаляют и контейнер, и том: docker rm -f pagila-lesson && docker volume rm pagila-data. Для compose то же самое делает docker compose down -v. Флаг -v удаляет тома, то есть все данные — на проде так не делают.

!
ЛОВУШКА POSTGRES 18: СТАРЫЕ ТУТОРИАЛЫ

Почти во всех статьях в интернете написано -v pgdata:/var/lib/postgresql/data. Для образов до 17 включительно это правильно. С postgres:18 контейнер с таким томом не запустится:

Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster" (specifically, using major-version-specific directory names). ... The suggested container configuration for 18+ is to place a single mount at /var/lib/postgresql ...

(Это настоящий вывод официального скрипта.) Начиная с 18 том подключают к /var/lib/postgresql, как в compose-файле Pagila. Мораль: читайте страницу образа на Docker Hub, а не первый ответ в поиске.

Именованный том -v имя:/путьBind mount -v ./папка:/путь
Где лежат данныев служебной папке Docker (docker volume inspect покажет /var/lib/docker/volumes/pagila-data/_data)в вашей папке, видно в Finder/проводнике
Для чегоданные баз, всё, что должно пережить контейнерконфиги, SQL-скрипты, исходники при разработке (правите в редакторе — контейнер сразу видит)

Кеш слоёв: почему порядок строк важен

Поменяйте любую строку в server.js (например, текст в console.log) и соберите ещё раз:

Docker идёт по строкам сверху вниз. Если входные данные слоя не изменились, слой берётся из кеша. Как только какой-то слой изменился, все слои ниже пересобираются. А теперь «наивный» Dockerfile, который часто пишут первым:

Плохо: COPY . . до npm ci
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
CMD ["node", "server.js"]

Правка server.js → изменился слой COPY . . → npm ci заново: added 14 packages, 1,23 с вместо 0,30 с.

Хорошо: сначала package*.json
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

Правка server.js меняет только последний слой. npm ci пересоберётся, только когда изменятся зависимости.

У нас 14 пакетов, и разница — секунда. В реальном фронтенд-проекте с 1500 пакетами это минуты на каждую сборку в CI. Правило: то, что меняется редко, — выше; то, что часто, — ниже.

08 · Сети: контейнеры знакомятся

live-coding~10 мин

Запускаем API. База работает на localhost:5433, правда? Пробуем:

◆
ГЛАВНОЕ ПРАВИЛО: LOCALHOST ВНУТРИ КОНТЕЙНЕРА — ЭТО САМ КОНТЕЙНЕР

У каждого контейнера своя сеть (namespaces из блока 02). localhost внутри films-api — это films-api, а там на порту 5432 никого нет. Порт 5433 открыт на вашем компьютере, а не в контейнере API. Это самая частая ошибка при первом знакомстве с Docker.

Правильно — положить оба контейнера в одну пользовательскую сеть. Внутри неё работает встроенный DNS: контейнеры находят друг друга по имени.

Откройте http://localhost:3000/films?limit=3 в браузере — то же самое. Обратите внимание: rental_rate пришёл строкой "0.99". Это NUMERIC из урока про DDL: драйвер pg специально не превращает его в число JavaScript, чтобы не потерять точность.

 ваш компьютер              сеть pagila-net (свой DNS)
   localhost:3000 ──-p──▶  films-api      172.18.0.3
                                │  pagila-lesson:5432
                                ▼
   localhost:5433 ──-p──▶  pagila-lesson  172.18.0.2  (Postgres)
РАЗБОР
КодЧто значитЗачем так
docker network create pagila-netсвоя сеть типа bridgeв ней работает DNS по именам контейнеров. В сети по умолчанию — нет: там getent hosts pagila-lesson ничего не нашёл
--network pagila-netподключить контейнер к сети при запускеdocker network connect — подключить уже работающий

порт 5432, а не 5433внутри сети — «родной» порт контейнера5433 — это проброс на ваш компьютер, внутри сети он не нужен
!
ЗЕРКАЛЬНАЯ ЛОВУШКА: СЕРВЕР СЛУШАЕТ 127.0.0.1

Если программа внутри контейнера слушает только 127.0.0.1, проброс -p не поможет. Я проверил на Node-сервере с listen(3001, '127.0.0.1'): изнутри контейнера он отвечает, а снаружи curl: (56) Recv failure: Connection reset by peer. Именно так по умолчанию ведёт себя Vite (npm run dev). В контейнере его запускают с vite --host (то есть 0.0.0.0 — «все интерфейсы»). Наш server.listen(3000) без адреса слушает все интерфейсы, поэтому всё работает.

→
А ЕСЛИ БАЗА НЕ В КОНТЕЙНЕРЕ?

Если контейнеру нужен сервис на вашем компьютере (например, Postgres, установленный без Docker), в Docker Desktop есть специальное имя host.docker.internal: -e DB_HOST=host.docker.internal -e DB_PORT=5433. На Linux его нужно включить флагом --add-host=host.docker.internal:host-gateway.

09 · Уборка, Docker Desktop и прод

теория + команды~5 мин

Docker быстро съедает диск: образы, кеш сборки, забытые тома. В Docker Desktop всё это видно на вкладках Containers (логи, кнопки Stop/Delete, вкладка Exec — терминал внутри), Images и Volumes. Из терминала:

КомандаЧто удаляет
docker rm -f имяконтейнер (слой записи). Именованные тома остаются
docker rmi имяобраз, если на него нет контейнеров
docker container pruneвсе остановленные контейнеры
docker image pruneобразы без тега (<none>) — остатки пересборок
docker volume prune -aтома без контейнеров — с данными, осторожно
docker system pruneостановленные контейнеры, сети, образы <none>, кеш сборки

Как это выглядит на проде

 git push ──▶ CI: docker build -t films-api:1.4.0 ──▶ тесты ВНУТРИ этого образа ──▶ docker push в реестр
                                                                                      │
 сервер:  docker pull films-api:1.4.0  ◀──────────────────────────────────────────────┘
          docker run ... films-api:1.4.0      (тот же образ, байт в байт)

Это называют неизменяемой инфраструктурой (immutable infrastructure). На сервер не заходят «поправить файлик». Новая версия = новый образ с новым тегом, старая версия остаётся в реестре, и откат — это запуск прошлого тега. Фронтенд в проде тоже часто живёт в контейнере: собранная папка dist раздаётся nginx-образом.
