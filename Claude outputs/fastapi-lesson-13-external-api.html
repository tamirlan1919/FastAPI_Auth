Интеграция с внешними API

До сих пор auth-api общался только со «своими»: базой, Redis, RabbitMQ, Celery. Всё это мы запускаем сами и можем перезапустить. Сегодня наш сервер впервые пойдёт в чужой сервис, который мы не контролируем. Он может ответить через 10 секунд, поменять формат ответа, ограничить нас лимитом запросов или просто лечь. Возьмём настоящий API — GitHub — и сделаем карточку разработчика для блога: имя, аватар, год регистрации и три самых популярных репозитория. Главное в уроке не сам запрос (это одна строка), а всё, что вокруг: один клиент на приложение, проверка ответа, кэш, понятные ошибки, повторы и тесты без интернета.

ЧТО ПОЯВИТСЯ В AUTH-API

  • GET /github/{login} — карточка разработчика из двух запросов к GitHub, с кэшем в Redis: 2 мс вместо секунды.
  • Клиент GitHubClient: один на всё приложение, создаётся в lifespan, с таймаутом, повторами и своими исключениями.
  • Pydantic-модели ответа GitHub: из 33 полей берём 7 нужных, а изменение формата ловим сразу.
  • Честные ошибки для фронтенда: 404, 502, 503 с Retry-After — вместо «500 Internal Server Error».
  • 7 тестов клиента без интернета через httpx.MockTransport.

МОК, КОТОРЫЙ ВРЁТ

Это классика: «все тесты зелёные, а на проде ничего не работает». Мок повторяет то, что разработчик думает о внешнем API. Если разработчик ошибся в адресе, мок ошибётся вместе с ним. Поэтому моки ставят на границе (вместо сети), а проверяют поведение: что наш код делает с ответом 200, 404, 500 и с таймаутом. И хотя бы раз руками проверяют настоящий API — что мы сейчас и сделаем.

Но через бэкенд мы прячем токены (их нельзя класть в JavaScript — его видит любой пользователь), кэшируем (лимит 60 запросов в час на всех, а не на каждого) и отдаём фронтенду свой стабильный формат: если GitHub что-то поменяет, исправим в одном месте на бэкенде.

02 · httpx: первые запросы

live-coding~12 мин

В Python есть популярная библиотека requests, но в FastAPI она не годится: она блокирующая. Пока requests.get() ждёт ответа секунду, event loop стоит (урок 12, блок 01), и весь сервер не отвечает никому. httpx умеет и синхронно (как requests), и асинхронно (await).

ПОЧЕМУ GATHER УСКОРЯЕТ ИМЕННО ЗДЕСЬ

Это I/O-bound работа из урока 12: процессор почти ничего не делает, 95% времени — ожидание сети. Пять ожиданий можно «наложить» друг на друга, и итог ≈ самому долгому запросу. Обратная сторона: пять одновременных запросов тратят лимит так же, как пять последовательных. А если вызвать gather для 1000 логинов, лимит кончится за секунду. Параллельность к чужому API всегда ограничивают (домашка со звёздочкой).

03 · Один клиент на всё приложение

live-coding~16 мин

В учебниках (и в вашем weather.py) часто пишут так: в каждом запросе async with httpx.AsyncClient() as client:. Работает, но каждый раз создаётся новое соединение: DNS, TCP, TLS-рукопожатие. Это несколько обменов сообщениями с сервером на другом конце света. Проверим, сколько это стоит.

В 3 раза медленнее на ровном месте. Клиент держит пул соединений: после первого запроса соединение с api.github.com остаётся открытым, и следующие запросы идут по нему без рукопожатий. Значит, клиент должен жить столько же, сколько приложение. Где у нас живут такие объекты? В lifespan: там уже лежат Redis (урок 8) и RabbitMQ (урок 10).

Настройки, lifespan, зависимость

Тот же приём, что с Redis в уроке 8: объект создаётся один раз при старте, эндпоинты получают его через Depends. В тестах зависимость можно подменить через app.dependency_overrides. Роутер github напишем после перерыва — пока закомментируйте строки с github.router, чтобы приложение запускалось.

!
CLIENT В ОБЫЧНОЙ ФУНКЦИИ — УТЕЧКА

Если создать httpx.AsyncClient() без async with и без aclose(), соединения останутся открытыми. Создавать клиент в каждом запросе с async with — безопасно, но медленно. Правильный вариант — один клиент на приложение и aclose() после yield в lifespan.

04 · Не доверяем ответу: модели Pydantic

live-coding~12 мин

Можно вернуть фронтенду response.json() как есть — так и сделано в учебниках. Но тогда фронтенд получит 33 поля GitHub, включая служебные, и любое изменение у GitHub сломает фронтенд. Правило: на границе с внешним миром всё проверяем. Мы уже делаем это с запросами от пользователя (UserCreate). Ответ чужого API — такие же непроверенные данные.

!
ALIAS ИЛИ VALIDATION_ALIAS

В учебных материалах для переименования пишут Field(alias='stargazers_count'). Я проверил, что тогда отдаст FastAPI с response_model: {'name': 'Spoon-Knife', 'stargazers_count': 14177}. alias работает в обе стороны: FastAPI по умолчанию сериализует ответ по алиасам, и фронтенд получит старое имя. validation_alias — только на вход: читаем stargazers_count, отдаём stars. С ним ответ: {'name': 'Spoon-Knife', ..., 'stars': 14177, ...}.

!
ЕЩЁ ДВЕ ОШИБКИ В ПРИМЕРЕ ИЗ УЧЕБНИКА

В примере с погодой в материалах урока except ValidationError есть, а from pydantic import ValidationError — нет: при первой же ошибке валидации вместо неё вылетит NameError. А return None при ошибке переносит проблему дальше: эндпоинт вернёт null со статусом 200, и фронтенд упадёт уже у себя. Ошибку нужно превратить в понятное исключение — так и делает наш клиент.

✦
ИСТОРИЯ: БАГ, КОТОРЫЙ ВИДЕН ТОЛЬКО СО ВТОРОГО РАЗА

Эту ошибку я не придумывал — поймал, когда проверял урок. Цепочка такая. В Redis мы сохранили карточку с полем stars (так модель называет его у себя). При чтении из кэша карточка снова проходит валидацию, а модель GitHubRepo принимает звёзды только из stargazers_count — это же модель для ответа GitHub. Первый запрос (без кэша) работает, поэтому при ручной проверке «один раз нажал — работает» баг не виден. Он появится на проде через минуту после деплоя.

Мораль: модель «как нам присылают» и модель «как мы отдаём» — разные модели, даже если поля почти совпадают. Смешали их — и формат GitHub протёк в наш кэш.

НЕ ПРОБРАСЫВАЙТЕ СТАТУС ЧУЖОГО API КАК СВОЙ

В материалах урока ошибки обрабатываются так: raise HTTPException(status_code=e.response.status_code, detail=f"...: {e.response.text}"). Представьте: у нашего токена GitHub истёк срок, GitHub отвечает 401. Наш сервер передаёт 401 фронтенду. А фронтенд на 401 делает что? Разлогинивает пользователя — хотя с его токеном всё в порядке, проблема у нас. Плюс в detail уходит текст чужого ответа, где может быть что угодно, вплоть до внутренних деталей. Статус нашего ответа должен описывать наш сервис: «нашёл / не нашёл / зависимость сломалась (502) / недоступна (503)». А подробности — в лог: logger.error('GitHub отклонил запрос ...').

Проверим клиент на настоящем GitHub

Таймаут в 1 мс не успевает даже установить соединение, поэтому причина — ConnectTimeout. Три попытки, две паузы, потом честное GitHubUnavailable. Заодно видно, как быстро тает лимит: 29 из 60. Его делили все, кто выходил в интернет с того же IP.

Сколько ждёт пользователь, если GitHub завис

Теперь главный вопрос. Пусть GitHub принимает соединение, но не отвечает (такое бывает при перегрузке). Сколько будет ждать фронтенд? Чтобы воспроизвести, я подменил GitHub «заглушкой», которая отвечает через 10 секунд, и выключил кэш.

16,5 секунды = 5 + 0,5 + 5 + 1 + 5. Пользователь давно закрыл вкладку, а мы всё это время держали соединение и три раза стучались в лежащий сервис. Правило: общее время = таймаут × попыток + паузы, и оно должно укладываться в то, сколько готов ждать человек (2–7 секунд). Для фоновых задач Celery бюджет может быть больше.

А если GitHub вообще недоступен (соединение отклонено), ответ приходит быстро: при retries=2 я получил 503 за 1,5 с: попытки падают мгновенно, остаются только паузы. Это хороший случай: «быстрый отказ» лучше медленного.

i
ПОЧЕМУ НЕ httpx.AsyncHTTPTransport(retries=2)

В httpx есть встроенные повторы: transport=httpx.AsyncHTTPTransport(retries=2). Они повторяют только ошибки соединения (ConnectError, ConnectTimeout). При 502 от GitHub или таймауте чтения они не сработают. И ещё ловушка, на которую я наткнулся при проверке: если передать свой transport, httpx перестаёт брать прокси из переменных окружения (HTTPS_PROXY). В сети, где интернет только через прокси, клиент сразу получил ConnectError: Temporary failure in name resolution. Свой цикл повторов прозрачнее и проверяется тестами.

07 · Тесты без интернета: MockTransport

live-coding~9 мин

Тесты, которые ходят в настоящий GitHub, медленные, тратят лимит и падают, когда в поезде нет интернета. Но и подменять AsyncClient.get, как в test_weather.py, плохо (шаг 0). В httpx есть способ лучше: подменить сеть. httpx.MockTransport(handler) — «транспорт», который вместо отправки запроса вызывает вашу функцию handler(request) и возвращает её ответ. Весь наш код — заголовки, разбор статусов, повторы, Pydantic — работает по-настоящему. Для этого в конструкторе клиента и есть параметр transport.

ТРИ ПРАВИЛА ДЛЯ КЛЮЧЕЙ

1) Ключи — только в .env, а .env — в .gitignore. Боты сканируют GitHub и находят утёкшие ключи за минуты. GitHub сам отзывает найденные в публичных репозиториях токены, а ключ от платного API могут успеть использовать за ваш счёт. 2) Ключи не пишем в логи: в нашем клиенте логируются путь и статус, а не заголовки. 3) Ключ к API — только на бэкенде. Всё, что попало в JavaScript, видит любой пользователь во вкладке Network.

GraphQL одним абзацем

В REST на каждую сущность свой URL, и сервер решает, какие поля отдать (у GitHub — 33). В GraphQL один адрес (POST https://api.github.com/graphql), а клиент в теле запроса сам перечисляет нужные поля и может за один запрос получить связанные данные. Из Python это всё тот же httpx.post:

Один запрос вместо двух, и сортировку по звёздам делает GitHub. Но есть два отличия от REST, о которых надо помнить. Первое: ошибку нельзя определить только по статусу. Неверное поле или несуществующий пользователь — это часто ответ 200 с полем errors, а raise_for_status() его не заметит. Второе: без токена GitHub GraphQL не работает вообще.
