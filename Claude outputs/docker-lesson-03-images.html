Образы: Dockerfile, многоэтапная сборка, теги

В первых двух уроках мы запускали чужие образы и написали один простой Dockerfile для films-api. Сегодня делаем то, что фронтендеру нужно чаще всего: упаковываем фронтенд. Начнём с Dockerfile «как получится» — он заработает, но образ будет весить 1,6 ГБ, внутри окажется секретный ключ, а в продакшене будет крутиться dev-сервер Vite. Шаг за шагом превратим его в образ на nginx, который в 5,5 раза легче, без Node.js и без секретов. А в конце научимся называть образы версиями, переносить и публиковать их.

ЧТО СДЕЛАЕМ ЗА УРОК

  • Заглянем в метаданные образа через docker image inspect и увидим, почему rm в отдельном слое не уменьшает образ: 494 МБ против 284 МБ.
  • Соберём фронтенд films-web (Vite + TypeScript) наивно и найдём в образе .env с ключом Stripe.
  • Сожмём контекст сборки с 66,3 МБ до 352 байт одним файлом .dockerignore.
  • Сделаем многоэтапную сборку: Node.js собирает, nginx раздаёт. 1,59 ГБ → 290 МБ, с официальными образами разница ещё больше.
  • Разберёмся с ARG и ENV — почему адрес API нельзя поменять через -e после сборки — и запустим films-api не от root.

01 · Образ изнутри: слои и метаданные

live~12 мин

Образ — это два слоя информации: файлы (стопка слоёв файловой системы, урок 1) и метаданные — инструкция, как из этих файлов запускать контейнер. Посмотрим метаданные образа films-api из прошлого урока:

ИнструкцияЧто создаётКогда работает
FROMберёт все слои базового образасборка
COPY, ADD, RUNновый слой файловсборка
WORKDIRпапку (крошечный слой) + метаданныесборка и запуск
CMD, ENTRYPOINT, EXPOSE, ENV, USER, LABELтолько метаданные, 0 байтзапуск
★
АНАЛОГИЯ ДЛЯ ФРОНТЕНДЕРА

Образ похож на опубликованный npm-пакет: файлы плюс package.json с полями main и scripts.start. Контейнер — это npm start этого пакета. Метаданные образа — его «package.json».

Слои только складываются

Главное правило слоёв, из которого вытекает половина советов по Dockerfile: каждый слой хранит только добавленное и изменённое. Если файл появился в слое 2, а удалён в слое 4, он всё равно лежит в слое 2 и занимает место. Проверим на установке curl:

Плохо: три RUN
FROM ubuntu:24.04
RUN apt-get update
RUN apt-get install -y --no-install-recommends curl
RUN rm -rf /var/lib/apt/lists/*
Хорошо: один RUN
FROM ubuntu:24.04
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

Мусор (кеш пакетного менеджера, временные файлы) нужно удалять в той же команде RUN, в которой он появился. Для npm то же самое: RUN npm ci && npm cache clean --force. А ещё лучше — многоэтапная сборка, где мусор вообще не попадает в итоговый образ (блок 05).

03 · .dockerignore: контекст сборки и секреты

live-coding~8 мин

Когда вы пишете docker build ., точка — это контекст сборки: папка, которую CLI упакует и отправит демону (урок 1: CLI и демон — разные процессы). COPY может взять только то, что есть в контексте. .dockerignore работает как .gitignore: перечисленное в контекст не попадает.

РАЗБОР .DOCKERIGNORE
СтрокаЗачем
node_modules, distставятся и собираются внутри образа под Linux

.env, .env.*секреты. Строка !.env.example — исключение из исключения: шаблон без значений можно
Dockerfile*, .dockerignoreсамому образу не нужны. Загляните в films-api: docker run --rm films-api ls -a /app покажет там Dockerfile — у него в .dockerignore этой строки нет
!
.DOCKERIGNORE — ПЕРВЫЙ ФАЙЛ, А НЕ ПОСЛЕДНИЙ

Если секрет хоть раз попал в образ, который ушёл в реестр, удалять его из Dockerfile поздно: старый образ уже скачан, а слой с файлом в нём остался навсегда (блок 01: слои только складываются). Ключ нужно перевыпускать. Поэтому .dockerignore создают вместе с Dockerfile, сразу.

!
ALPINE — НЕ БЕСПЛАТНО

В Alpine другая стандартная библиотека C — musl вместо glibc. Пакеты с нативным кодом (sharp для картинок, bcrypt, драйверы некоторых баз) публикуют отдельные сборки под musl, а если их нет — пытаются компилироваться и падают без python3 make g++. Ещё отличия: нет bash (только sh, урок 2: код 127), пакеты ставятся через apk add, а не apt-get. Для фронтенда, который в итоге раздаёт nginx, alpine почти всегда подходит идеально.

Знакомо любому, кто деплоил React Router или Vue Router: на главной всё работает, а обновление страницы /films/5 даёт 404. Файла films/5 нет, этот путь понимает только JavaScript-роутер. Нужно сказать nginx: «не нашёл файл — отдай index.html».

live-coding~10 мин

Vite заменяет import.meta.env.VITE_API_URL на строку в момент npm run build. После сборки в JS-файле просто лежит текст адреса. Проверим:

◆
ПОЧЕМУ ТАК: ФРОНТЕНД ВЫПОЛНЯЕТСЯ НЕ В КОНТЕЙНЕРЕ

Переменные окружения видит процесс в контейнере — nginx. А наш JavaScript выполняется в браузере пользователя, у которого никакого VITE_API_URL нет. Поэтому для фронтенда «одна сборка — разные окружения» делают иначе: собирают отдельный образ на каждое окружение через --build-arg, относительный адрес /api плюс прокси в nginx, или config.json, который фронт загружает при старте. Бэкенд (films-api) читает process.env при запуске, и для него -e работает.

!
ARG — НЕ ДЛЯ СЕКРЕТОВ

Значения ARG сохраняются в истории образа того этапа, где использовались:

docker history --no-trunc films-web:buildstage → RUN |1 VITE_API_URL=https://api.pagila.example /bin/sh -c npm run build

(это я собрал только первый этап: --target build). Передай так токен — и любой с доступом к образу его прочитает. В итоговом образе многоэтапной сборки истории первого этапа нет, но полагаться на это не стоит. Для секретов при сборке есть RUN --mount=type=secret. А в браузерный код секреты не кладут никогда: всё, что попало в JS, видит каждый пользователь.

08 · Теги, перенос образа, реестр

live~12 мин

Полное имя образа: [реестр/][пользователь/]имя:тег. Без реестра подразумевается Docker Hub, без тега — latest. Тег — это ярлык на конкретный образ, и ярлыков у одного образа может быть сколько угодно:

Теперь поменяем заголовок в main.ts и пересоберём с тем же тегом latest:

!
ПОЧЕМУ LATEST В ПРОДАКШЕНЕ — ПЛОХО

latest не значит «самый новый». Это просто тег, который ставится, когда другого не указали, и он переезжает при каждой сборке. Сервер с films-web:latest после перезапуска может поднять другую версию. А откатиться «на прошлый latest» нельзя: у него нет имени. Поэтому выпускают с версией (1.0.1, SemVer) или с хешем коммита (films-web:3f9c2a1), а latest оставляют для удобства локально.

i
КУДА ДЕЛАСЬ СТАРАЯ ВЕРСИЯ LATEST

В методичке сказано, что после пересборки старый образ становится <none>:<none> («висячий», dangling), и его чистят docker image prune. Так ведёт себя классическое хранилище образов. В новых версиях Docker с хранилищем containerd (как у меня, Docker 29) старый образ просто исчез из списка: docker images -f dangling=true пусто, docker image prune → Total reclaimed space: 0B, а его слои остаются в кеше сборки (docker system df, строка Build Cache, чистится docker builder prune). Посмотрите, что у вас.

Перенос без интернета: save и load

Так переносят образы на сервер без доступа в интернет или отдают заказчику на флешке. В обычной жизни образы переносят через реестр.

Публикация в Docker Hub

РеестрКогда
Docker Hubпубличные образы, учёба; бесплатно — публичные репозитории
GitHub Container Registry (ghcr.io), GitLab Registryобраз рядом с кодом, сборка в CI при каждом push

→
MAC С ПРОЦЕССОРОМ M И СЕРВЕР НА INTEL

Образ, собранный на Mac M1–M4, по умолчанию сделан под linux/arm64, а большинство серверов — linux/amd64. Запуск на сервере даст ошибку exec format error. Собирайте под нужную платформу: docker build --platform linux/amd64 -t ..., или сразу под обе через docker buildx build --platform linux/amd64,linux/arm64 --push. интерактив~13 мин
COPY . . → RUN npm ci: каждая правка в коде заново ставит зависимости.
Неправильный порядок слоёв. Сначала COPY package*.json ./ и npm ci, потом COPY . .
transferring context: 820MB, сборка начинается минуту.
Нет .dockerignore — в контекст уехали node_modules и .git.
Коллега нашёл в образе .env с ключами.
.env не в .dockerignore. Добавить и перевыпустить ключи — старый образ уже мог разойтись.
RUN apt-get update, RUN apt-get install, RUN rm -rf /var/lib/apt/lists/* — образ не уменьшился.
Слои только складываются. Одна команда RUN … && … && rm ….
Фронтенд-образ весит 1,5 ГБ, в проде работает npm run dev.
Нет многоэтапной сборки. Node собирает dist, nginx раздаёт.
После деплоя SPA обновление страницы /profile даёт 404.
nginx ищет файл /profile. try_files $uri $uri/ /index.html;
Передали -e VITE_API_URL=... при запуске, а фронт ходит на старый адрес.
Vite подставляет переменные при сборке. --build-arg или конфиг, который фронт грузит при старте.
FROM node — через полгода сборка в CI внезапно сломалась.
Тег latest уехал на новую мажорную версию. node:22-alpine или точная версия с хешем.
Образ с Mac на сервере: exec format error.
Собран под arm64. docker build --platform linux/amd64.

Домашнее задание

  1. Свой фронтенд. Возьмите свой React/Vue-проект (или PizzaHub) и напишите многоэтапный Dockerfile с nginx и try_files. Сравните размеры наивного и многоэтапного образов, запишите числа.
  2. Три базы. Соберите films-api на node:22, node:22-slim и node:22-alpine (меняется только FROM). Таблица: размер, время первой сборки, время пересборки после правки server.js.
  3. Прокси вместо запечённого адреса. Сделайте так, чтобы фронтенд ходил на относительный /api/films, а nginx проксировал /api/ в films-api (location /api/ { proxy_pass http://films-api:3000/; }). Запустите оба контейнера в одной сети (урок 1). Теперь один и тот же образ работает в любом окружении — почему?
  4. Аудит. Для своего образа выполните docker history --no-trunc и docker run --rm образ ls -la /app. Найдите хотя бы одну лишнюю вещь (файл, слой, переменную) и уберите её.
  5. Публикация. Зарегистрируйтесь на Docker Hub, опубликуйте films-web:1.0.1 и запустите его на компьютере соседа по парте одной командой docker run.
  6. Со звёздочкой: секрет при сборке. Представьте, что для npm ci нужен токен приватного npm-реестра. Передайте его через RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci и docker build --secret id=npmrc,src=.npmrc. Проверьте через docker history --no-trunc, что токена в образе нет.
