Docker Compose: весь стек одной командой

У нас есть три кусочка: база Pagila, API films-api и фронтенд films-web с прошлого урока. Каждый умеет жить в контейнере, но запускать их — это десяток длинных команд в правильном порядке. Сегодня описываем весь стек в одном файле compose.yaml и поднимаем его командой docker compose up. По дороге наступим на все грабли, на которые наступают в реальных проектах: «API стартовал раньше базы», CORS, «поменял пароль — не работает», «масштабировал — порт занят».

ЧТО СДЕЛАЕМ ЗА УРОК

  • Поднимем Pagila из compose-файла и поймём, откуда берутся имена контейнеров, сетей и томов.
  • Подключим API по имени сервиса db и увидим гонку: 4 секунды API отвечает ECONNREFUSED, пока база грузится. Лечим healthcheck + depends_on: condition — и находим healthcheck, который врёт.
  • Вынесем пароль в .env и поймаем ошибку «поменял пароль — база не пускает».
  • Добавим фронтенд: увидим настоящую ошибку CORS в браузере, разберём, почему fetch('http://api:3000') из методички не работает, и починим всё прокси в nginx.
  • Сделаем режим разработки через compose.override.yaml: код с диска, node --watch для API, Vite с горячей перезагрузкой.
  • Освоим ежедневные команды и масштабирование: три копии API и nginx, который раздаёт им запросы по очереди.

✦
АНАЛОГИЯ: ПАРТИТУРА

Dockerfile — это ноты для одного музыканта: как собрать один образ. compose.yaml — партитура оркестра: кто играет, в каком порядке вступает, кто кого слышит. Вы не раздаёте музыкантам указания по одному — вы кладёте партитуру и говорите «играем» (docker compose up).

★
ФРОНТЕНДЕРАМ ЭТО ЗНАКОМО

Это как package.json со скриптами: вместо «запусти vite с такими флагами» вы пишете "dev": "vite --host" и запускаете npm run dev. Описали один раз — запускает любой. Только Compose описывает не команды, а желаемое состояние: «должны работать три сервиса вот с такими настройками». Если что-то уже работает как надо, Compose это не трогает.

ПОЧЕМУ pgvector, А НЕ postgres:18

Свежая схема Pagila делает CREATE EXTENSION vector — в ней есть таблица film_embedding с векторами. В чистом postgres:18 такого расширения нет, и загрузка схемы упадёт: ERROR: extension "vector" is not available. Поэтому в репозитории Pagila стоит build: . с Dockerfile, который доставляет расширение. Нам проще взять готовый образ pgvector/pgvector:pg18 — это официальный postgres:18 с уже установленным расширением.

→
YAML ЗА МИНУТУ

Вложенность — пробелами (табы запрещены), обычно по два. ключ: значение — словарь, - элемент — список. Строки можно без кавычек, но порты пишите в кавычках ("8080:80"): YAML 1.1 читает некоторые числа с двоеточием как время. Ошибка в отступе — самая частая ошибка новичка: Compose скажет, на какой строке.

Почти 4 секунды API отвечал 500: контейнер базы уже «запущен», но Postgres ещё грузит Pagila и не принимает подключения по сети. У меня загрузка заняла 4 секунды, на ноутбуке с Docker Desktop — может и 20. Если бы API при старте сразу шёл в базу (миграции, например), он бы просто упал.

Заметьте: 172.18.0.2 — это IP контейнера db. Имя превратилось в адрес — DNS работает. Проверить можно изнутри:

healthcheck: «жив» ≠ «готов»

Научим Docker проверять, что база действительно готова, и скажем API ждать именно этого:

РАЗБОР
КодЧто значитЗачем так
test: ["CMD-SHELL", "…"]команда внутри контейнера; код выхода 0 = здоровpg_isready есть в образе Postgres: «принимает ли сервер подключения»

HEALTHCHECK, КОТОРЫЙ ВРЁТ: ПОЧЕМУ -h 127.0.0.1

В интернете почти везде пишут pg_isready -U postgres. Посмотрите, что он отвечает, пока Pagila ещё загружается (я опрашивал оба варианта каждые полсекунды):

Во время загрузки скриптов официальный образ запускает временный Postgres, который слушает только unix-сокет внутри контейнера. pg_isready без -h ходит как раз через сокет — и честно говорит «готов», хотя по сети (а API ходит по сети) база ещё недоступна. С -h 127.0.0.1 проверка идёт по TCP — как у API — и врать перестаёт.

04 · .env и переменные

live-coding~8 мин

Пароль 123456 записан в compose.yaml дважды, а этот файл лежит в git. Вынесем его. Compose сам читает файл .env из папки проекта и подставляет переменные в ${…}:

РАЗБОР
ЗаписьЕсли переменной нет
${DB_PASSWORD}предупреждение и пустая строка — легко не заметить
${DB_PASSWORD:-123456}значение по умолчанию
${DB_PASSWORD:?текст}ошибка с вашим текстом, ничего не запускается

Предупреждение — от строки в api, ошибка — от строки в db. Что Compose реально подставил, показывает docker compose config — итоговый файл после всех подстановок:

!
ДВА РАЗНЫХ .env

Файл .env рядом с compose.yaml — для подстановки ${…} в сам compose-файл. В контейнеры он не попадает. env_file: .env в сервисе — передать все переменные файла в контейнер. Методичка их смешивает. Мы используем первый: так в compose.yaml видно, какой сервис какие переменные получает. И, конечно, .env — в .gitignore, а в git — .env.example.

«Поменял пароль — база не пускает»

Compose увидел новую переменную и пересоздал оба контейнера. API пришёл с новым паролем. Но POSTGRES_PASSWORD используется только при первой инициализации — а том уже не пустой, там старый пароль. Варианты: вернуть старый пароль; сменить его в самой базе (ALTER USER postgres PASSWORD '…'); или, если данные не жалко, docker compose down -v.

05 · Фронтенд и CORS: браузер не живёт в Docker

live-coding~17 мин

Добавим films-web из прошлого урока — многоэтапный Dockerfile: Node собирает, nginx раздаёт. Сначала «в лоб», как есть:

Страница пришла с localhost:8080, а запрос идёт на localhost:3000 — другой порт = другой origin. Браузер такой ответ читать не даёт, пока сервер явно не разрешит (заголовок Access-Control-Allow-Origin). Наш API таких заголовков не ставит.

«Тогда напишу http://api:3000, как в методичке»

В методичке на схеме фронтенд делает fetch('http://backend:3000'). Попробуем — соберём с VITE_API_URL=http://api:3000:

◆
ГДЕ ВЫПОЛНЯЕТСЯ КОД ФРОНТЕНДА

Контейнер web только отдаёт файлы — index.html и JS. Выполняет этот JS браузер на вашем компьютере, а он не в сети Docker и про имя api ничего не знает. Имена сервисов работают только между контейнерами. Это главная мысль блока: в Docker-сети живут nginx, API и база, а браузер — снаружи, и ему доступно только то, что открыто через ports.

 ваш компьютер                        сеть films_default (Docker)
 ─────────────                        ───────────────────────────
 браузер ── localhost:8080 ─────────▶ web (nginx) ── http://api:3000 ──▶ api ── db:5432 ──▶ db
         ✗ http://api:3000            знает имена сервисов
           (такого имени снаружи нет)

Решение: nginx проксирует /api

Пусть браузер ходит туда же, откуда пришла страница — на /api/…, а nginx внутри Docker-сети передаёт эти запросы в api. Один origin — CORS не нужен. Это домашка №3 с прошлого урока, сделаем её вместе.

proxy_pass http://api:3000/;передать запрос сервису apinginx — внутри сети, имя api он знает. Слэш в конце отрезает префикс: /api/films → /films. Без слэша API получил бы /api/films и ответил 404
proxy_set_header …передать исходный Host и IP клиентачтобы API в логах видел настоящий адрес, а не адрес nginx

А ЕСЛИ ФРОНТЕНД И API НА РАЗНЫХ ДОМЕНАХ?

Бывает: app.example.com и api.example.com. Тогда прокси не поможет — API должен отвечать заголовками CORS (в Express — пакет cors, в FastAPI — CORSMiddleware). Но если можно сделать один домен с /api, так проще и быстрее: нет лишнего запроса OPTIONS перед каждым «сложным» запросом.

Итоговый файл хорош для запуска, но не для работы: поменяли строчку в server.js — пересобирай образ. Для разработки нужно другое: код с диска, автоперезапуск, открытые порты API и базы. Писать второй файл целиком не нужно — Compose умеет накладывать файлы друг на друга.

НА WINDOWS И MAC ИНОГДА НЕ ЛОВИТ ИЗМЕНЕНИЯ

Я проверял на Linux, где изменения файлов в bind mount приходят мгновенно. В Docker Desktop это обычно тоже работает, но если правки не подхватываются (особенно когда проект лежит в файловой системе Windows, а не в WSL), включите опрос: для Vite — server: {'{'} watch: {'{'} usePolling: true {'}'} {'}'} в vite.config.ts. БАЗА ИЗ DBEAVER

В режиме разработки база открыта на localhost:5433 (5432 занят вашей Pagila из первого урока). Подключение в DBeaver: хост localhost, порт 5433, база pagila, пользователь postgres, пароль из .env. В режиме «как в проде» порта нет — снаружи база недоступна, и это правильно.

Отладка: чек-лист «не работает»

  1. docker compose ps — все ли Up? Restarting, Exited (1), (unhealthy) → смотрим логи этого сервиса.
  2. docker compose logs --tail 50 сервис — первая ошибка обычно говорит всё.
  3. Сервис не видит другой → docker compose exec api getent hosts db. Нет ответа — опечатка в имени или сервисы в разных проектах/сетях.
  4. Настройки не те → docker compose config: что на самом деле подставилось.
  5. Образ старый → docker compose up -d --build.

Масштабирование: три копии API

Попробуем как в методичке, но в режиме разработки, где у api открыт порт 3000:

Порт 3000 на компьютере один — вторая копия его не получит. В режиме «как в проде» у api портов нет, и всё получается:

DNS Docker отдаёт на имя api все три адреса, а nginx, получив несколько адресов, сам раскидывает запросы по очереди (round-robin). Это и есть «балансировщик перед сервисами» из методички — он у нас уже был.

!
ДВЕ ЛОВУШКИ МАСШТАБИРОВАНИЯ

1. nginx узнаёт адреса один раз — при старте. Если увеличить число копий, когда nginx уже работает, новые копии не получат запросов, пока не выполнить docker compose restart web. 2. Обычный up -d возвращает одну копию. Я пересобрал web командой up -d --build web — и api-2, api-3 исчезли: без --scale Compose приводит всё к описанному в файле. Нужно постоянно три — пишите в файле deploy: replicas: 3.

08 · Игра «Что пошло не так?», шпаргалка, домашка

интерактив~13 мин
API в логах: connect ECONNREFUSED 172.18.0.2:5432 первые секунды после up, потом всё работает.
depends_on без условия. Он ждёт старта контейнера, а не готовности базы. healthcheck + condition: service_healthy.
Healthcheck есть, db healthy, а API всё равно пару секунд получает отказ.
pg_isready без -h проверяет unix-сокет, а во время загрузки скриптов сервер слушает только его. pg_isready -h 127.0.0.1.
Поменяли DB_PASSWORD в .env → password authentication failed.
POSTGRES_PASSWORD работает только на пустом томе. Вернуть пароль, ALTER USER или down -v.
Склонировали проект в другую папку — база пустая, хотя «вчера всё было».
Имя проекта = имя папки → другой том. name: в начале compose.yaml.
Фронтенд: net::ERR_NAME_NOT_RESOLVED для http://api:3000.
JS выполняется в браузере, а браузер не в сети Docker. Относительный /api + прокси в nginx (или Vite).
Фронтенд: blocked by CORS policy при запросе на localhost:3000.
Другой порт = другой origin. Прокси /api через тот же origin или CORS-заголовки в API.
/api/films через nginx отдаёт 404 от API.
Нет слэша в конце proxy_pass http://api:3000/ — API получает /api/films вместо /films.
После docker compose down -v пропали все пользователи из базы.
-v удаляет тома. Обычный down данные не трогает.
--scale api=3: Bind for 0.0.0.0:3000 failed: port is already allocated.
Опубликованный порт у масштабируемого сервиса. Порт открывает только прокси, у api — без ports.
Поменяли environment в compose.yaml, сделали docker compose restart api — ничего не изменилось.
restart не перечитывает файл. docker compose up -d пересоздаст контейнер с новыми настройками.
Прод-контейнер web бесконечно перезапускается без логов.
Dev-сборка записалась под прод-тегом — в образе CMD node. Разные image: для dev и прод, пересобрать.

  2. pgAdmin в стек. Добавьте сервис pgadmin (образ dpage/pgadmin4, порт 5050:80, переменные PGADMIN_DEFAULT_EMAIL и PGADMIN_DEFAULT_PASSWORD — из .env). Подключитесь к базе. Какой хост вписать в pgAdmin: localhost или db? Почему?
