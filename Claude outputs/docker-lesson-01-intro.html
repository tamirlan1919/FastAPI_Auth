Введение в Docker

Два урока мы писали PizzaHub с паттернами. Сегодня научимся его упаковывать: так, чтобы он одинаково запускался у вас, у коллеги на Windows и на сервере в облаке, без фразы «а у меня работает». Docker — не «инструмент для админов». Это то, с чем фронтенд сталкивается каждый день: CI, превью-сборки, локальные базы данных, деплой. После этого урока вы сможете поднять любую базу одной командой и собрать образ своего приложения.

ЧТО СДЕЛАЕМ ЗА УРОК

  • Разберёмся, зачем нужны контейнеры: история про морские контейнеры, виртуальные машины и «у меня работает».
  • Поймём устройство: образ, контейнер, слои, реестр, демон и CLI — на простых аналогиях.
  • Руками в терминале: hello-world, сайт на nginx, своя страница PizzaHub через -v, Redis и Postgres за минуту.
  • Упакуем PizzaHub: напишем Dockerfile и .dockerignore, соберём образ, ускорим сборку в 20 раз за счёт правильного порядка слоёв.
  • Посмотрим, как это живёт в проде: неизменяемые образы, CI, что будет на следующих уроках.

ПОДГОТОВКА — ОТПРАВЬТЕ ГРУППЕ ЗА ДЕНЬ

Самая частая причина сорванного урока по Docker — у половины группы он не установлен или образы качаются 20 минут через медленный Wi-Fi. Попросите студентов заранее:

1. Установить Docker Desktop (docker.com → Get Docker) и запустить его — в трее/меню должен появиться кит. Пользователям Windows — включить режим WSL 2 (Docker Desktop предложит сам).
2. Выполнить в терминале одну команду — она скачает всё, что нужно на уроке:

docker pull hello-world && docker pull nginx && docker pull redis:8 && docker pull postgres:17 && docker pull node:22-alpine && docker pull node:16-alpine

3. Иметь проект PizzaHub после урока 2 по паттернам (pizzahub-lesson2.zip). Если его нет — раздайте архив: Dockerfile мы пишем именно для него.

Часть 1 · Зачем и как устроено

01 · «У меня работает!» и немного истории

теория~12 мин
Docker упаковывает приложение вместе со всем, что ему нужно для запуска, в один переносимый «контейнер».Запустился у вас — запустится где угодно, где есть Docker.

Боль, знакомая каждому

Вы склонировали проект коллеги. npm install — ошибки. Оказывается, у него Node 22, у вас Node 18. Поставили Node 22 — теперь не собирается ваш старый проект. На сервере вообще Linux, а у вас Windows, и пути с \ ломают скрипт. Добавьте сюда базу данных нужной версии, Redis, переменные окружения… Это называют «матрицей ада» (matrix of hell): N приложений × M окружений, и каждая клетка — свой сюрприз.

☺
МЕМ, С КОТОРОГО ВСЁ НАЧАЛОСЬ

— У меня на машине всё работает!
— Отлично, тогда отправим в продакшен твою машину.

Шутка стала реальностью: Docker делает ровно это — упаковывает «вашу машину» (точнее, всё, что нужно приложению) и отправляет её куда угодно.

✦
ИСТОРИЯ: ЖЕЛЕЗНЫЙ ЯЩИК, КОТОРЫЙ ИЗМЕНИЛ МИР

До 1950-х корабли грузили вручную: мешки, бочки, ящики разных форм. Погрузка одного судна занимала дни, грузчики носили всё на спине, половина времени корабль стоял в порту. В 1956 году американский предприниматель Малкольм Маклин отправил из Нью-Джерси судно с 58 одинаковыми стальными ящиками — первыми интермодальными контейнерами. Кран ставит контейнер на корабль, потом на поезд, потом на грузовик, и никто не заглядывает внутрь. Стоимость погрузки упала в десятки раз, и это во многом сделало возможной глобальную торговлю.

Docker — та же идея для программ: стандартный «ящик», который одинаково грузится на ноутбук, сервер или в облако, неважно, что внутри — Node, Python или Java. Поэтому на логотипе Docker кит, который несёт на спине контейнеры.

ИСТОРИЯ: ПЯТЬ МИНУТ НА PYCON

Контейнеры в Linux существовали и до Docker, но пользоваться ими было больно. В марте 2013 года Соломон Хайкс из маленькой компании dotCloud вышел на конференцию PyCon с пятиминутным «молниеносным» докладом «The future of Linux Containers» и показал Docker. Через несколько месяцев проект был одним из самых обсуждаемых на GitHub, а компания переименовалась в Docker Inc. Сегодня в контейнерах запускается большая часть бэкенда в мире, включая Kubernetes, на котором крутятся крупнейшие сервисы.

ОДИН ОБРАЗ — МНОГО КОНТЕЙНЕРОВ

Как из одного класса можно создать сколько угодно объектов, так из одного образа nginx можно запустить десять независимых контейнеров. Удалили контейнер — образ остался, можно запустить новый. Это главное, что нужно запомнить сегодня.

Слои: почему Docker быстрый

Образ — это не один большой архив, а стопка слоёв. Каждая инструкция в Dockerfile добавляет слой сверху:

  ┌────────────────────────────────────┐
  │ слой для записи контейнера         │  ← создаётся при запуске; логи, временные файлы. Удалили контейнер — исчез
  ╞════════════════════════════════════╡
  │ 4. ваш код (src/, data/)          │  ← меняется часто
  │ 3. node_modules (npm ci)          │  ← меняется редко
  │ 2. package.json                   │
  │ 1. Alpine Linux + Node.js 22      │  ← не меняется никогда, скачан один раз
  └────────────────────────────────────┘
         слои образа — только для чтения
  • Кеш. Поменяли код — Docker пересобирает только слой 4, нижние берёт из кеша. Сборка за секунды вместо минут. В блоке 09 увидим это вживую.
  • Экономия места. Десять образов на node:22-alpine хранят базовый слой один раз — на всех.
  • Контейнер = образ + тонкий слой для записи. Всё, что приложение запишет на диск, попадёт в этот верхний слой и пропадёт вместе с контейнером. Поэтому базы данных хранят в томах (блок 06).

Кто с кем общается: клиент, демон, реестр

✦
АНАЛОГИЯ: РЕСТОРАН

Вы (терминал, команда docker ...) — посетитель. Docker CLI — официант: принимает заказ и несёт на кухню. Docker Daemon (dockerd) — кухня: она реально готовит (скачивает образы, собирает, запускает контейнеры). Docker Hub — оптовый склад, откуда кухня берёт продукты, если их нет в холодильнике. Посетитель на кухню не ходит — только через официанта.

  терминал                  ваш компьютер                                  интернет
┌────────────┐  REST API  ┌──────────────────────────────┐   pull/push   ┌──────────────┐
│ docker CLI │ ─────────▶ │ Docker Daemon (dockerd)      │ ◀───────────▶ │ Docker Hub   │
│ docker run │            │  образы · контейнеры · тома  │               │  nginx, node │
└────────────┘            └──────────────────────────────┘               │  postgres... │
  Docker Desktop UI,                                                     └──────────────┘
  VS Code — тоже клиенты API

Демон слушает REST API. CLI — лишь один из клиентов; Docker Desktop, расширение VS Code или ваш Python-скрипт шлют демону те же JSON-запросы. Поэтому всё, что сделано мышкой в Docker Desktop, видно в терминале, и наоборот.

!
А КАК ЖЕ MAC И WINDOWS?

Контейнеры используют механизмы ядра Linux (namespaces — «свои стены» для процесса, cgroups — «лимиты по памяти и процессору»). У macOS и Windows другое ядро. Поэтому Docker Desktop тихо запускает внутри маленькую виртуальную машину с Linux, и контейнеры живут в ней. Отсюда две практические вещи: Docker Desktop нужно запустить перед работой (иначе ошибка Cannot connect to the Docker daemon), и ему нужна оперативная память — настройки → Resources.

04 · nginx: порты и управление контейнерами

практика~12 мин

hello-world вывел текст и завершился. Теперь запустим что-то, что работает долго, — веб-сервер nginx (тот самый reverse proxy из урока по паттернам).

Часть командыЧто значит
docker runсоздать контейнер из образа и запустить его
-d (detach)запустить в фоне и вернуть терминал. Без флага логи nginx займут терминал, а Ctrl+C остановит контейнер
-p 8080:80проброс порта: ВАШ_ПОРТ:ПОРТ_В_КОНТЕЙНЕРЕ. Внутри nginx слушает 80, снаружи стучимся на 8080
--name my-siteимя контейнера. Без него Docker придумает смешное вроде quirky_hopper
nginxимя образа (без тега = nginx:latest)
◆
ПОЧЕМУ НУЖЕН -p

У контейнера своя изолированная сеть — «квартира с закрытой дверью». nginx внутри слушает порт 80, но снаружи туда никто не попадёт. -p 8080:80 — «прорубить окно»: всё, что приходит на localhost:8080 вашего компьютера, пересылается на порт 80 контейнера. Порядок важен и часто путается: слева — снаружи, справа — внутри.

Откройте http://localhost:8080 — увидите «Welcome to nginx!». Обновите страницу пару раз и посмотрите логи:

КомандаАналогия
docker ps«Диспетчер задач» для контейнеров
docker logsконсоль браузера DevTools для контейнера
docker stop / startсвернуть и развернуть программу — данные внутри сохраняются
docker rmудалить программу — слой записи контейнера пропадает
→
ЭКСПЕРИМЕНТ НА 2 МИНУТЫ: ОДИН ОБРАЗ — ТРИ КОНТЕЙНЕРА

Запустите docker run -d -p 8081:80 --name site2 nginx и docker run -d -p 8082:80 --name site3 nginx. Три независимых сервера из одного образа — вот она, аналогия «класс и объекты». Затем попробуйте занять уже занятый порт: docker run -d -p 8081:80 nginx → ошибка port is already allocated. Два процесса не могут слушать один порт — ни в Docker, ни без него (вспомните, как ругается Vite, когда 5173 занят). Уберите за собой: docker rm -f site2 site3.

Мышкой: всё то же самое есть в Docker Desktop во вкладке Containers: Stop, Delete, клик по имени — логи, вкладка Exec — терминал внутри контейнера.

05 · Своя страница PizzaHub через -v

практика~10 мин

«Welcome to nginx» — скучно. Покажем в nginx свою страницу. Но образ nginx чужой, внутрь него мы ничего не писали. Решение — bind mount: подключить папку с вашего компьютера внутрь контейнера.

создаёмpizzahub/site/index.htmlрольПростая статическая страница меню. Папку site создаём в корне проекта PizzaHub, рядом с src.
ЧастьЧто значит
-v ПАПКА_У_ВАС:ПАПКА_В_КОНТЕЙНЕРЕподключить папку. Снова: слева — снаружи, справа — внутри
$(pwd) / ${PWD}текущая папка. Docker требует абсолютный путь, поэтому не пишем просто ./site — в старых версиях это не работало
/usr/share/nginx/htmlпапка, откуда nginx отдаёт файлы. Это написано в описании образа на Docker Hub — читать описание образа полезно всегда
:roread-only: контейнер может читать файлы, но не менять их. Сайту писать в папку незачем, а защита бесплатная
\ в конце строкиперенос длинной команды в bash (в PowerShell пишем в одну строку)
Проверка: если my-site ещё жив и занимает 8080 — сначала docker rm -f my-site. Откройте http://localhost:8080 — страница PizzaHub. Теперь поменяйте в index.html цену Маргариты, сохраните и обновите браузер — изменения видны сразу, без перезапуска контейнера. Папка не скопирована, а подключена.
◆
BIND MOUNT vs ТОМ

Bind mount (-v /путь/на/компьютере:...) — конкретная папка, которую вы видите и редактируете. Удобно в разработке: правите код в IDE — контейнер видит сразу. Именованный том (-v имя:...) — папкой управляет Docker, где она лежит, вам знать не обязательно. Удобно для данных баз (блок 06). Отличить просто: начинается с / или . — bind mount, просто имя — том.

postgres:17конкретная мажорная версия. Не latest: обновление базы с версии на версию — отдельная процедура, внезапно получить его при pull не хочется
→
ЭКСПЕРИМЕНТ: ДАННЫЕ ПЕРЕЖИВАЮТ КОНТЕЙНЕР

1. Создайте таблицу: docker exec -it dev-pg psql -U postgres -c "CREATE TABLE pizzas(name text); INSERT INTO pizzas VALUES ('Маргарита');"
2. Удалите контейнер совсем: docker rm -f dev-pg
3. Запустите новый той же командой с тем же -v pizzahub-pgdata:...
4. docker exec -it dev-pg psql -U postgres -c "SELECT * FROM pizzas;" — Маргарита на месте. Контейнер новый, а данные в томе остались. Без -v таблица бы исчезла.

☺
ИСТОРИЯ ИЗ ЖИЗНИ

Классика первых недель с Docker: разработчик поднимает Postgres без тома, неделю наполняет тестовыми данными, потом делает «уборку» docker rm -f $(docker ps -aq) — а новый контейнер стартует с пустой базой. Строго говоря, данные остались в безымянном томе, который Docker создал сам, но найти его среди десятка томов с именами вроде 3f9a1c… — тот ещё квест. Контейнеры одноразовые (эфемерные), и это не баг, а принцип. Всё ценное — в тома.

Удалить всё после урока: docker rm -f dev-redis dev-pg pizzahub-site. Том с данными Postgres при этом останется; удалить его — docker volume rm pizzahub-pgdata.

практика~6 мин

Помните, в уроках по паттернам мы использовали structuredClone для глубокой копии (Prototype, Memento)? Эта функция появилась только в Node 17. Проверим, что будет на сервере, где «исторически» стоит Node 16, — для этого не нужно ничего устанавливать:

Две версии Node на одном компьютере, без nvm, за две секунды, и ни одна не установлена в систему. И главное — если мы упакуем PizzaHub в образ на node:22-alpine, ошибка «на сервере старый Node» станет невозможной: Node 22 едет внутри образа вместе с кодом. Это и есть решение «матрицы ада».

08 · Dockerfile для PizzaHub

live-coding~14 мин
Dockerfile — рецепт образа: построчные инструкции «возьми базу, скопируй, установи, запусти».Каждая инструкция — новый слой.
создаёмpizzahub/DockerfileрольРецепт образа PizzaHub. Файл в корне проекта, рядом с package.json. Имя ровно Dockerfile — с большой буквы и без расширения.

Разбор каждой инструкции

ИнструкцияЧто делаетАналогия для фронтендера
FROM node:22-alpineбазовый образ — с него начинается наш. Всегда первая строкаextends — наследуемся от готового класса
WORKDIR /appсоздать папку /app внутри образа и перейти в неё (mkdir + cd)корень проекта
COPY package.json package-lock.json ./скопировать файлы с вашего компьютера в /app образа. Слева — откуда, справа — куда—
RUN npm ciвыполнить команду при сборке образа; результат (node_modules) сохраняется в слойnpm ci — как npm install, но строго по package-lock.json, без обновлений. Для сборок только так
COPY . .скопировать весь проект (кроме того, что в .dockerignore)—
CMD ["npm", "run", "dev"]команда при запуске контейнера. Записана как JSON-массивскрипт start в package.json
!
RUN ИЛИ CMD — САМАЯ ЧАСТАЯ ПУТАНИЦА

RUN выполняется один раз при сборке (docker build) — «приготовить заготовки». CMD выполняется при каждом запуске (docker run) — «подать блюдо». RUN может быть много, CMD — одна (если написать две, сработает последняя). А почему CMD массивом, а не строкой CMD npm run dev? Строка запускается через оболочку sh, и Ctrl+C/docker stop приходят оболочке, а не вашему приложению. Массив запускает программу напрямую.

.dockerignore — что НЕ отправлять в сборку

создаёмpizzahub/.dockerignoreрольРаботает как .gitignore, но для COPY. Тоже в корне проекта. Имя начинается с точки.
✦
ИСТОРИЯ: ПОЧЕМУ node_modules — ПЕРВАЯ СТРОКА

Без .dockerignore команда COPY . . скопирует в образ и ваш локальный node_modules — поверх того, что только что аккуратно поставил RUN npm ci. Проблема в том, что некоторые пакеты содержат программы, собранные под конкретную ОС. В PizzaHub это esbuild, на котором работает tsx. На Mac или Windows установится версия для Mac/Windows, а внутри контейнера Linux. Итог — загадочная ошибка вида You installed esbuild for another platform than the one you're currently using. Плюс лишние сотни мегабайт в «посылке» для сборки. Правило: node_modules всегда ставится внутри образа, а снаружи игнорируется.

Остальные строки: .git — история репозитория в образе не нужна (и может содержать секреты); site — страница для nginx из блока 05 к приложению не относится; Dockerfile и .dockerignore — рецепт внутри торта не нужен.

Собираем и запускаем

ЧастьЧто значит
docker buildсобрать образ по Dockerfile
-t pizzahubtag — имя образа (и версия после двоеточия, по умолчанию latest)
. (точка!)контекст сборки — папка, файлы из которой можно копировать через COPY. Точку в конце забывают постоянно — получают requires 1 argument
Готово: весь сценарий урока 2 по паттернам отработал внутри Linux-контейнера с Node 22 — даже если у вас на компьютере Windows и Node 18. Этот же образ можно запустить у коллеги или на сервере: результат будет тот же.
→

09 · Слои и кеш: почему порядок строк важен

live-coding~10 мин

Поменяем код и пересоберём. Допишите в конец src/main.ts любую строку, например console.log('👋 из Docker');, и снова docker build -t pizzahub .:

Docker проверяет слои сверху вниз: «изменилось ли что-то, от чего зависит этот шаг?». package.json не менялся — значит, npm ci даст то же самое, берём из кеша. Изменился только код — пересобирается только последний слой.

А если написать «очевидно»?

◆
ПОЧЕМУ ТАК

Кеш слоя сбрасывается, если изменилось хоть что-то, что в него копируется, — и вместе с ним сбрасываются все слои ниже. В «плохом» варианте COPY . . зависит от любого файла проекта, поэтому любая правка кода ломает кеш и тянет за собой npm ci. В нашем замере: 0.2 секунды против 4.1 — в 20 раз. В настоящем фронтенд-проекте с сотнями зависимостей npm ci идёт минуту-две, и разница превращается в «пересобрал за секунду» против «пошёл за кофе» на каждую правку. Правило: то, что меняется редко, — выше; то, что часто, — ниже.

Код весит 200 КБ, зависимости — 66 МБ (в основном это esbuild для tsx). Поэтому и важно, чтобы тяжёлый слой не пересобирался из-за лёгкого.

11 · Docker в продакшене и что дальше

теория~6 мин

Неизменяемая инфраструктура

Раньше на сервер заходили по SSH и обновляли код «руками»: git pull, npm install, перезапуск. Каждый сервер постепенно становился уникальной «снежинкой», и никто точно не знал, что на нём стоит. С Docker принцип другой — immutable infrastructure: сервер ничего не собирает, он только запускает готовые образы.

 git push ──▶ CI (GitHub Actions)
               1. docker build -t pizzahub:a1b2c3d .     ← тег = хеш коммита
               2. тесты ВНУТРИ этого образа
               3. docker push в реестр
                         │
                         ▼
               сервер: docker pull pizzahub:a1b2c3d → docker run
               тот же самый образ, байт в байт, что прошёл тесты

Что-то сломалось после релиза — запускаем предыдущий тег, откат за секунды. Риск «на тесте работало, а на проде другая версия библиотеки» сводится к нулю: тестировали и запускаем буквально один и тот же образ.

★
ГДЕ ФРОНТЕНДЕР ВСТРЕЧАЕТ DOCKER

Сборка фронтенда в CI идёт в контейнере node:22. Превью-окружения для каждого pull request. Прод фронтенда часто выглядит как «собрали статику в образе node, положили в образ nginx» — это называется multi-stage build, его разберём дальше. Плюс Playwright и Cypress гоняют e2e-тесты в своих официальных Docker-образах с браузерами.

Что будет на следующих уроках

  • Сети — как контейнер с бэкендом находит контейнер с базой по имени.
  • Docker Compose — вместо пяти длинных docker run один файл compose.yaml и одна команда docker compose up: бэкенд + Postgres + Redis + nginx.
  • Multi-stage build — маленькие и безопасные образы для прода.

Домашнее задание

  1. Своя страница. Запустите nginx с любой своей HTML-страницей (портфолио, лендинг) на порту 3000 через bind mount. Поменяйте страницу и убедитесь, что изменения видны без перезапуска.
  2. Две версии. Соберите pizzahub:1.0, поменяйте что-нибудь в сценарии main.ts, соберите pizzahub:1.1. Запустите обе версии и сравните вывод. Посмотрите docker images: сколько места занимает вторая версия «сверху» первой и почему почти нисколько?
  3. Версия Node. Поменяйте в Dockerfile node:22-alpine на node:16-alpine, пересоберите и запустите. Запишите ошибку и объясните её. Верните 22.
