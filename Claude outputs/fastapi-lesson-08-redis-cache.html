Кеширование и Redis

В auth-api уже есть пользователи в SQL, задачи в MongoDB и вход по JWT. Всё работает — но каждый запрос честно идёт в базу, даже если ответ не менялся час. Сегодня научим приложение запоминать ответы и подключим Redis — самый быстрый «блокнот» бэкенд-разработчика. Начнём с простого — что такое кеш, пара команд в консоли — и к концу урока дойдём до вещей, которые делают в настоящем продакшене: logout для JWT и защиты от перебора паролей.

ЧТО ПОЯВИТСЯ В AUTH-API К КОНЦУ УРОКА

  • Redis подключён через lifespan и зависимость RedisDep, как у нас сделаны SQL-сессии.
  • Счётчик визитов /stats/visits — первый «привет» от Redis.
  • Кеш для GET /users/ и GET /users/{username}, заголовок X-Cache: HIT/MISS, сброс кеша при регистрации и смене email.
  • CacheService — переиспользуемый Cache-Aside, который не роняет API, если Redis упал.
  • POST /auth/logout — настоящий выход для JWT через чёрный список токенов.
  • Защита /auth/token: 5 неверных паролей за 15 минут → 429 Too Many Requests.

Часть 1 · Просто о кеше

01 · Что такое кеш

теория~8 мин
Кеш — это быстрая память для ответов, которые дорого получать заново.Один раз посчитали — запомнили — дальше отдаём готовое.
✦
ИСТОРИЯ ПРО МОЛОКО

Вам захотелось молока. Можно каждый раз идти в магазин: одеться, спуститься, отстоять очередь — 20 минут. А можно держать пакет в холодильнике — 5 секунд. Магазин — это база данных: там есть всё и всегда свежее, но идти долго. Холодильник — это кеш: быстро, но места мало, и у молока есть срок годности. Запомните эту картинку — весь урок будет про неё:

  • молоко есть в холодильнике → cache hit (попадание);
  • холодильник пуст → идём в магазин и кладём пакет в холодильник → cache miss (промах);
  • срок годности на пакете → TTL (time to live);
  • молоко скисло раньше срока, выкидываем → инвалидация;
  • холодильник забит, выкидываем то, что давно не трогали → вытеснение (eviction).
   запрос GET /users/
          │
          ▼
   ┌──────────────┐   есть    ┌──────────────────┐
   │ есть в кеше? │──────────▶│ отдать из кеша   │──▶ ответ за ~1 мс   HIT
   └──────┬───────┘           └──────────────────┘
          │ нет
          ▼
   ┌──────────────┐           ┌──────────────────┐
   │ сходить в БД │──────────▶│ положить в кеш   │──▶ ответ за ~50 мс  MISS
   └──────────────┘           │ на 60 секунд     │
                              └──────────────────┘

Насколько быстрее — порядок цифр

Если растянуть время так, чтобы чтение из оперативной памяти (~100 наносекунд) длилось 1 секунду, то:

ОперацияРеально (порядок)«В человеческих секундах»
чтение из RAM~100 нс1 секунда
чтение с SSD~100 мкс~17 минут
поход по сети внутри дата-центра~0.5 мс~1.5 часа
тяжёлый SQL-запрос с JOIN-ами~50 мс~6 дней
внешний API (погода, оплата)~300 мс~1 месяц
☺
ПРИКОЛ

С кешем пользователь получает ответ «за секунду», без кеша он «ждёт посылку неделю». Похожая таблица — «Latency numbers every programmer should know» — гуляет по интернету больше 15 лет, её связывают с Джеффом Дином из Google. Цифры в ней со временем меняются, а пропорции нет.

Что кешировать, а что нет

Кешируем
  • читают часто, меняют редко (список пользователей, каталог, настройки);
  • дорого получать (тяжёлый SQL, внешний API, отчёт);
  • не страшно показать устаревшее на 30–60 секунд.
Не кешируем
  • деньги и остатки на складе в момент покупки;
  • то, что меняется при каждом запросе;
  • то, что и так быстро достаётся (кеш тоже стоит денег и сложности).
◆
ГЛАВНЫЙ КОМПРОМИСС

Кеш — это всегда сделка: мы платим свежестью данных за скорость. Копия в кеше может отставать от базы. Вся сложность кеширования — в ответе на вопрос «насколько отставать допустимо и как вовремя выкинуть устаревшее».

02 · Почему Redis, а не dict в Python

теория~7 мин

Первая мысль питониста: «Зачем отдельная база? Положу ответ в словарь!»

Локально работает. А вот в продакшене всё разваливается:

  • Несколько процессов. В проде запускают uvicorn --workers 4 или несколько контейнеров. У каждого процесса свой словарь. Сбросили кеш в одном — в остальных трёх живут старые данные, и пользователь видит то старый email, то новый, в зависимости от того, в какой воркер попал.
  • Перезапуск = пустой кеш. Задеплоили — и все запросы разом ломятся в базу.
  • Нет срока годности. Словарь сам ничего не удаляет и растёт, пока не съест всю память.
   dict в каждом процессе                      один Redis на всех
 ┌──────────┐ ┌──────────┐ ┌──────────┐      ┌──────────┐ ┌──────────┐ ┌──────────┐
 │ worker 1 │ │ worker 2 │ │ worker 3 │      │ worker 1 │ │ worker 2 │ │ worker 3 │
 │ {старое} │ │ {новое}  │ │ {старое} │      └────┬─────┘ └────┬─────┘ └────┬─────┘
 └──────────┘ └──────────┘ └──────────┘           └──────┬─────┴────────────┘
   три разные «правды»                               ▼
                                                    ┌──────────┐
                                                    │  Redis   │  одна общая правда
                                                    └──────────┘

Redis в двух словах

Redis (REmote DIctionary Server) — это, по сути, тот же словарь, но вынесенный в отдельный сервер, общий для всех процессов, со сроком годности у ключей. Данные лежат в оперативной памяти, поэтому операция занимает доли миллисекунды.

✦
ИСТОРИЯ

2009 год, Сицилия. Сальваторе Санфилиппо (ник antirez) делает стартап с аналитикой посещений сайтов в реальном времени, и MySQL не успевает за потоком данных. Он пишет маленький сервер «словарь в памяти» для себя — так появился Redis. Через несколько лет его использовали Twitter, GitHub, Instagram и Stack Overflow, а потом, наверное, и каждый второй бэкенд.

Продолжение истории: в 2024 году компания Redis сменила открытую лицензию на более закрытую, и сообщество под крылом Linux Foundation сделало форк — Valkey. В 2025-м Redis 8 снова получил открытую лицензию (AGPL). Для нас разницы нет: команды и Python-клиент одинаковые.

Чем Redis лучше словаря

☺
ПАРАДОКС

Redis выполняет команды в одном потоке — и при этом это одна из самых быстрых баз в мире. Секрет в том, что всё лежит в памяти, а каждая команда занимает микросекунды: очередь не успевает накопиться. Бонус однопоточности — INCR не может «потерять» прибавку, даже если 1000 запросов пришли одновременно.

ПОЧЕМУ ДВОЕТОЧИЯ В КЛЮЧАХ

У Redis нет таблиц и папок — только плоский список ключей. Поэтому принято именовать их как пути: сущность:id:что — user:alice, stats:visits, blacklist:abc123. По префиксу легко найти ключи (SCAN MATCH user:*), а GUI вроде Redis Insight показывают их деревом, как папки.

!
ЗАПРЕЩЁННАЯ КОМАНДА

В интернете вы встретите KEYS * — «покажи все ключи». Локально можно. В продакшене — никогда: на миллионе ключей Redis займётся только этим и на секунды перестанет отвечать всем (помним — он однопоточный). В интернете полно историй, как сайт ложился от одной такой команды из консоли. Используйте SCAN — он перебирает ключи порциями.

Проверка: у всех PING → PONG, ключ с EX 10 исчез через 10 секунд. Консоль не закрываем — через 10 минут будем смотреть, что туда кладёт наше приложение.
Часть 2 · Redis в auth-api

04 · Подключаем Redis к FastAPI

live-coding~10 мин

Шаг 1. Библиотека

  • redis — официальный Python-клиент (он же redis-py). Асинхронная версия живёт внутри него: redis.asyncio.
  • [hiredis] — дополнительный быстрый парсер ответов на C. Необязателен, но бесплатно ускоряет.
!
НЕ СТАВЬТЕ AIOREDIS

В старых статьях и курсах пишут pip install aioredis. Это была отдельная библиотека, которую в 2022 году влили в redis-py (версия 4.2) — с тех пор старый пакет заброшен. Сегодня «aioredis» — это просто import redis.asyncio.

Шаг 2. Настройки

меняемapp/core/config.pyчтоДобавляем адрес Redis и TTL кеша по умолчанию. Остальное как было.

redis://localhost:6379/0 — протокол, хост, порт и номер базы. В одном Redis 16 независимых баз (0–15): например, приложение — в /0, тесты — в /15, и они не мешают друг другу. В проде адрес приходит из .env: REDIS_URL=redis://:пароль@redis-host:6379/0.

Шаг 3. Модуль подключения

создаёмapp/db/redis.pyрольЗнает, как создать клиент Redis и как отдать его в эндпоинт. Рядом с database.py (SQL) и mongo.py — все подключения к хранилищам в одной папке.
  • Redis.from_url(...) создаёт не одно соединение, а пул соединений: запросы берут из него свободное соединение и возвращают обратно. Поэтому клиент создаём один раз на приложение, а не на каждый запрос.
  • decode_responses=True — Redis хранит байты. Без этого флага await redis.get(...) вернёт b'{"id": 1}', с ним — обычную строку '{"id": 1}'.
  • Таймауты по 1 секунде — если Redis «завис», мы быстро получим ошибку, а не повесим весь запрос пользователя. Кеш, который тормозит сильнее базы, хуже, чем никакого.

Шаг 4. Жизненный цикл — lifespan

заменяемapp/main.pyчтоДобавляем lifespan: создать клиент при старте, закрыть при остановке. Заодно убираем неиспользуемые импорты (ensure_future, Depends, старую init_db — схемой давно управляет Alembic) и подключаем роутер stats. Его файл создадим в следующем блоке — чтобы приложение запустилось уже сейчас, создайте пустой app/api/routers/stats.py с двумя строками: from fastapi import APIRouter и router = APIRouter().
◆
ПОЧЕМУ LIFESPAN

Код до yield выполняется один раз при старте, после yield — при остановке. Клиент кладём в app.state — общий «рюкзак» приложения, доступный из любого запроса. ping() на старте — это fail fast: забыли запустить Redis — приложение не стартует с понятной ошибкой, а не «падает у пользователя через час». aclose() аккуратно закрывает пул (в старых примерах встречается close() — он устарел).

Шаг 5. Зависимость

дописываемapp/api/deps.pyкудаИмпорты — наверх, RedisDep — рядом с SessionDep.

Тот же приём, что у нас с SessionDep и UserRepoDep: эндпоинт пишет redis: RedisDep, а FastAPI сам вызывает get_redis и подставляет клиент. В тестах эту зависимость легко подменить через app.dependency_overrides.

05 · Первый эндпоинт: счётчик визитов

live-coding~5 мин

Начинаем с самого простого, что вообще можно сделать с Redis, — счётчика. Никакого кеша, никакой базы.

создаёмapp/api/routers/stats.pyрольМаленький роутер «пощупать Redis»: проверка связи и счётчик визитов.
◆
ПОЧЕМУ INCR, А НЕ GET + SET

Наивный вариант: v = get() → set(v + 1). Если два запроса придут одновременно, оба прочитают 5 и оба запишут 6 — один визит потерялся. Это гонка (race condition). INCR делает «прочитать + прибавить + записать» одной командой внутри Redis, а Redis выполняет команды строго по очереди. Потерять прибавку невозможно — даже при 4 воркерах и 10 000 запросов в секунду.

Проверка: в консоли redis-cli из блока 03 наберите GET stats:visits — там то же число, что вернул API. Приложение и консоль смотрят в один и тот же Redis.

06 · Cache-Aside: кешируем GET /users/

live-coding~12 мин
Cache-Aside — «кеш сбоку»: приложение само смотрит в кеш, а если пусто — само идёт в базу и само кладёт результат в кеш.Самый популярный паттерн кеширования. База про кеш ничего не знает.
  1. Придумать ключ — «название полки в холодильнике»: users:all.
  2. GET по ключу. Есть значение → HIT, отдаём сразу.
  3. Нет → MISS: запрос в базу → превратить результат в строку (JSON) → SET с TTL → отдать.

Было

Первая попытка — и первая ошибка

Логичная мысль: «Redis хранит строки — сделаю json.dumps от того, что вернул репозиторий». Пробуем:

◆
ПОЧЕМУ

Репозиторий возвращает ORM-объекты SQLAlchemy — «живые» объекты, связанные с сессией базы, а не данные. json не знает, как их записать (и правильно делает: внутри лежит, например, hashed_password, которому не место в кеше ответа). Нам нужен путь ORM → Pydantic-схема → JSON. Схема UserOut у нас уже есть, и в ней from_attributes=True — она умеет читать ORM-объекты.

Рабочая версия

заменяемapp/api/routers/users.pyчтоЭндпоинт GET /users/ с кешем. Остальные эндпоинты не трогаем.

Разберём каждую деталь

  • USERS_ALL_KEY = "users:all" — ключ в константе. Его будут использовать и чтение, и (скоро) сброс кеша. Опечатка в одном месте = кеш, который никто никогда не сбросит.
  • if cached is not None, а не if cached — пустой список "[]" — тоже валидный закешированный ответ, и он не должен считаться промахом.
  • model_validate(u) — ORM-объект → схема UserOut (поле hashed_password отбрасывается). model_dump(mode="json") — схема → обычный dict, где всё уже JSON-совместимо (даты станут строками и т.д.).
  • ex=60 — TTL 60 секунд. Даже если мы забудем сбросить кеш, через минуту данные обновятся сами — страховка от вечно устаревших данных.
  • response: Response — FastAPI подставит объект ответа, чтобы мы могли добавить свой заголовок. X-Cache: HIT/MISS — не стандарт, а удобная для отладки традиция: похожий заголовок ставят CDN и кеширующие прокси, например Fastly и Varnish.

Смотрим, как это работает

Мы не зря держим echo=True в database.py: SQLAlchemy печатает каждый запрос в консоль. Вызываем GET /users/ два раза подряд и смотрим консоль uvicorn:

☺
ПОДВОХ ДЛЯ ВНИМАТЕЛЬНЫХ

Если отключить наш кеш и вызвать эндпоинт ещё раз, SQLAlchemy напишет [cached since 0.012s ago]. «Так он и так кеширует?!» Нет: SQLAlchemy кеширует скомпилированный текст SQL, чтобы не собирать строку запроса заново. Данные он всё равно каждый раз берёт из базы. Хороший вопрос группе на внимательность.

→
ЭКСПЕРИМЕНТ: ПОЧУВСТВОВАТЬ РАЗНИЦУ

SQLite с тремя пользователями отвечает за миллисекунду — разницу не заметить. Временно добавьте в начало UserRepo.get_users строку await asyncio.sleep(2) («представим, что это тяжёлый отчёт») и не забудьте import asyncio. Первый запрос — 2 секунды, следующие 60 секунд — мгновенно. После эксперимента строку уберите.

Проверка: в Swagger первый GET /users/ → заголовок x-cache: MISS, второй → HIT. В redis-cli: GET users:all — JSON со списком, TTL users:all — сколько секунд осталось жить.

07 · Динамические ключи: GET /users/{username}

live-coding~8 мин

Список — это один ключ на всех. А профиль у каждого пользователя свой. Если кешировать профиль под ключом "user", то первый, кто зайдёт, станет «профилем для всех».

08 · Инвалидация кеша

live-coding~10 мин

САМАЯ ИЗВЕСТНАЯ ШУТКА ПРО КЕШ

«В информатике есть только две сложные вещи: инвалидация кеша и придумывание имён». — Фил Карлтон, инженер Netscape. Народная версия: «...две сложные вещи: инвалидация кеша, придумывание имён и ошибки на единицу».

Ответ на вопрос с перерыва: пользователь сменил email, а GET /users/ ещё 50 секунд отдаёт старый. Молоко скисло раньше срока годности. Есть две стратегии:

СтратегияКакПлюсы / минусы
TTLждём, пока ключ истечёт сампросто; но до N секунд показываем старое
Явная инвалидацияизменили данные → сами удаляем ключисвежо сразу; но нужно помнить все места, где данные меняются

На практике делают обе сразу: явно сбрасываем, а TTL оставляем страховкой на случай, если где-то забыли.

Где в auth-api меняются пользователи

  • Регистрация POST /auth/register — в списке появился новый пользователь → устарел users:all.
  • Смена email — такого эндпоинта ещё нет, сделаем PATCH /users/me → устарели users:all и user:{username}.

ПОЧЕМУ СНАЧАЛА БАЗА, ПОТОМ КЕШ

Если сначала удалить кеш, а потом обновить базу, то в промежутке (миллисекунды!) другой запрос может успеть: кеш пуст → читает из базы ещё старый email → кладёт его в кеш на 60 секунд. Наша инвалидация пропала зря. Порядок «база → удалить кеш» сужает это окно почти до нуля. И именно удаляем, а не записываем новое значение: следующий запрос сам аккуратно загрузит свежие данные.

09 · CacheService: убираем копипасту

live-coding~12 мин

Посмотрите на два наших эндпоинта: в каждом одни и те же 8 строк «get → если есть, вернуть → загрузить → set». Добавим кеш для задач из Mongo — будет третья копия. И у всех трёх копий одни и те же проблемы:

  1. Redis упал — API упал. Остановите контейнер (docker stop auth-redis) и вызовите GET /users/ → 500 Internal Server Error. Кеш должен ускорять, а он стал точкой отказа. База-то жива!
  2. Сменили схему — сломали кеш. Добавили в UserOut обязательное поле — старые JSON в Redis больше не проходят валидацию → ошибка у пользователя.
  3. Ключи разбросаны строками по разным файлам: "users:all" в users.py, ещё раз в auth.py…

Решаем всё сразу: выносим Cache-Aside в один класс.

создаёмapp/core/cache_keys.pyрольЕдинственное место, где придумываются имена ключей. Все остальные файлы вызывают эти функции.
◆
ЗАЧЕМ ВЕРСИЯ В КЛЮЧЕ

Поменяли формат UserOut — поднимаем CACHE_VERSION до "v2". Новый код читает ключи v2:..., которых ещё нет, — честный MISS и загрузка из базы. Старые v1:... никто не читает, и через 60 секунд они истекут сами. Ни одной ошибки валидации и ни одного ручного FLUSHALL при деплое.

создаёмapp/services/cache.pyрольВесь Cache-Aside в одном методе get_or_set плюс invalidate. Ничего не знает про пользователей: работает с любыми данными, для которых есть Pydantic-тип.

Разбор по шагам — от простого к хитрому

  • loader — функция «как достать данные, если в кеше пусто». Сервис не знает, откуда данные — из SQL, Mongo или внешнего API. Это и делает его переиспользуемым.
  • TypeAdapter — способ Pydantic превращать в JSON и обратно любой тип, а не только модель: TypeAdapter(list[UserOut]) умеет dump_json(список) и validate_json(строка).
  • T = TypeVar("T") — «какой тип вернёт loader, такой вернёт и get_or_set». IDE и mypy будут знать, что из кеша пришёл именно list[UserOut].
  • except RedisError → идём в базу. Это стратегия fail-open: кеш сломался — работаем медленнее, но работаем. Пользователь не заметит, а в логах будет предупреждение.
  • except ValidationError — в кеше лежит что-то неожиданное (старая схема, руками записанный мусор) — считаем, что это MISS.
  • if value is None: return None, False — «не нашли» не кешируем (наш 404 из блока 07 переехал сюда).
  • ttl + random.randint(0, ttl // 10) — разброс TTL на 0–10%. Зачем — в истории ниже.
✦
ИСТОРИЯ: «ТАБУН» (CACHE STAMPEDE)

Представьте: в 12:00:00 после деплоя прогрели кеш для тысячи страниц, все с TTL ровно 60 секунд. В 12:01:00 все ключи истекают одновременно, и тысячи запросов разом ломятся в базу — она падает. Это называют cache stampede или «эффектом табуна». Случайный разброс TTL «размазывает» истечение по времени. Для самых горячих ключей добавляют ещё и блокировку: в базу идёт только первый запрос, остальные ждут (это в домашке).

дописываемapp/api/deps.pyчтоЗависимость CacheDep — сразу под RedisDep. Импорты наверх: from app.core.config import settings и from app.services.cache import CacheService.
заменяем целикомapp/api/routers/users.pyчтоЭндпоинты стали короткими: «как загрузить» + один вызов сервиса. Ручной json и redis.get/set исчезли.

ИСКЛЮЧЕНИЕ ИЗ ПРАВИЛА

fail-open — правильная стратегия для кеша. Но в блоке 10 Redis будет хранить чёрный список токенов, и там мы поступим наоборот — fail-closed: нет связи с Redis → не пускаем. Лучше пользователь перелогинится, чем вор с украденным токеном пройдёт, потому что «проверка временно недоступна».

10 · Logout для JWT: чёрный список

live-coding~11 мин

В учебном материале по Redis обычно показывают «сессии в Redis»: при логине генерируется session_id, в Redis кладётся session:{id} → user, и при каждом запросе мы ищем его там. У нас же вход по JWT (урок 4) — и у JWT есть знаменитая проблема, которую Redis решает идеально.

✦
ИСТОРИЯ: БИЛЕТ В КИНО

JWT — как бумажный билет с печатью: контролёр смотрит на печать (подпись) и время сеанса (exp) и пропускает — в базу он не звонит. Быстро! Но если вы потеряли билет, «отменить» его нельзя: кто нашёл, тот и пройдёт. В нашем auth-api то же самое: «Выйти» на фронте просто удаляет токен из браузера, а сам токен ещё 30 минут валиден. Украли — пользуйся.

Решение: дать контролёру стоп-лист — список номеров отменённых билетов. Нужен быстрый (проверка на каждом запросе) и со сроком годности (через 30 минут билет истечёт сам, хранить его в стоп-листе дольше незачем). Это ровно Redis.

 POST /auth/logout  (с токеном, jti = 7f3a...)
        │
        ▼
 Redis: SET blacklist:7f3a "1" EX <сколько токену осталось жить>

 GET /users/me  (тот же токен)
        │
        ▼
 подпись ок → exp ок → EXISTS blacklist:7f3a? ── да ──▶ 401
                                              └── нет ──▶ 200

Шаг 1. У каждого токена — свой номер

Чтобы внести токен в стоп-лист, его надо как-то назвать. В стандарте JWT для этого есть поле jti (JWT ID).

меняемapp/core/security.pyчтоФункция create_access_token добавляет jti. Импорт наверх: from uuid import uuid4.

Шаг 2. Сервис чёрного списка

создаёмapp/services/token_blacklist.pyрольДве операции: «отозвать токен» и «отозван ли токен».
  • exp в расшифрованном токене — Unix-время (секунды с 1970 года). exp - time.time() — сколько токену осталось жить.
  • ex=seconds_left — запись в стоп-листе исчезнет ровно тогда, когда токен истёк бы сам. Чёрный список никогда не разрастается: в нём только «живые» отозванные токены.
  • EXISTS — самая дешёвая проверка: значение нам не нужно, только факт наличия.

Шаг 3. Проверяем на каждом запросе

меняемapp/api/deps.pyчтоВ get_current_user добавляем параметр redis: RedisDep и одну проверку. Импорт: from app.services.token_blacklist import is_token_revoked.

Все эндпоинты с CurrentUserDep (/users/me, PATCH /users/me…) получили проверку автоматически — мы поменяли одну зависимость, а не десять эндпоинтов. Вот за что мы любим Depends.

Шаг 4. Эндпоинт выхода

  • current_user: CurrentUserDep — мы его не используем, но он гарантирует, что выйти может только тот, у кого валидный и ещё не отозванный токен.
  • oauth2_scheme вызывается дважды (тут и внутри CurrentUserDep)? Нет: FastAPI кеширует зависимости в рамках одного запроса и вызовет её один раз.
  • 204 No Content — «готово, сказать нечего». Тела ответа нет.
i
А КАК ЖЕ «СЕССИИ В REDIS»?

Классические серверные сессии — та же идея, вывернутая наоборот: в Redis хранится белый список (session:{id} → user_id с TTL), а клиент получает только случайный id в cookie. Выход — DEL session:{id}. Плюс: полный контроль (выкинуть пользователя со всех устройств). Минус: поход в Redis на каждый запрос — как и у нашего чёрного списка. JWT + blacklist — популярный компромисс: проверяем только отозванные, а их мало.

11 · Защита логина от перебора

live-coding~8 мин
✦
ИСТОРИЯ

Сейчас наш /auth/token можно долбить скриптом бесконечно: перебор по словарю популярных паролей — тысячи попыток в минуту. В 2014 году на GitHub выложили утилиту iBrute: она перебирала пароли через API «Найти iPhone», где не было ограничения на число попыток. Apple закрыла дыру за пару дней. Мораль: любой эндпоинт входа без лимита — открытая дверь для перебора. Защита — rate limiting: «не больше 5 попыток за 15 минут». Для счётчика с таймером Redis подходит идеально — вспоминаем INCR из блока 05.

создаёмapp/services/rate_limit.pyрольСчитает попытки входа по имени пользователя в «окне» 15 минут. Шестая попытка → 429.

Разбор

  • Алгоритм «фиксированного окна»: ключ login_attempts:alice = число попыток; ключ живёт 15 минут с первой попытки, потом исчезает — и счёт начинается заново.
  • pipeline(transaction=True) — несколько команд отправляются одним пакетом и выполняются подряд, без вклинивания чужих команд (MULTI/EXEC в терминах Redis). Без этого: сделали INCR, а сервер упал до EXPIRE — ключ остался без срока годности, и пользователь заблокирован навсегда.
  • expire(..., nx=True) — «поставь таймер, только если его ещё нет». Иначе каждая новая попытка продлевала бы блокировку. (Опция NX у EXPIRE есть с Redis 7.)
  • await pipe.execute() возвращает результаты всех команд списком: [новое_число_попыток, True].
  • 429 + Retry-After — стандартный HTTP-ответ «слишком много запросов, повторите через N секунд». Фронтенд может показать таймер.
итоговая версияapp/api/routers/auth.pyчтоРегистрация с инвалидацией (блок 09), логин с ограничением попыток и logout (блок 10) — полностью.
◆
ПОЧЕМУ ПО ИМЕНИ, А НЕ ПО IP

Ограничение по имени защищает конкретный аккаунт от перебора, и наоборот — злоумышленник может «заблокировать» чужой аккаунт, специально вводя неверный пароль. Ограничение по IP (request.client.host) защищает от одного бота, но «бьёт» по целому офису за одним IP. В бою ставят оба. Для остальных эндпоинтов обычно берут готовую библиотеку — например, slowapi или fastapi-limiter, оба работают поверх Redis.

12 · Когда кончится память

теория~6 мин

Redis хранит всё в оперативной памяти, а она не бесконечна. Что будет, когда холодильник забит? Это решает настройка maxmemory-policy:

ПолитикаЧто выкидываетКогда
noevictionничего; новые записи получают ошибкупо умолчанию. Хорошо, если Redis — хранилище, а не кеш
allkeys-lruдавно не использованные ключи — из всехклассика для чистого кеша
volatile-lruдавно не использованные — только среди ключей с TTLкеш и «вечные» данные в одном Redis
allkeys-lfuредко используемые (по частоте)есть явные «горячие» ключи
volatile-ttlключи, которым меньше всего осталось житьредко

LRU = Least Recently Used, «давно не трогали». Холодильник: выкидываем банку, которую никто не открывал с прошлого года.

!
ВАЖНО ДЛЯ НАШЕГО ПРОЕКТА

У нас в одном Redis лежат и кеш, и чёрный список токенов, и счётчики попыток. С allkeys-lru Redis при нехватке памяти может выкинуть запись blacklist:... — и отозванный токен «оживёт». Варианты: volatile-lru не поможет (у blacklist тоже есть TTL) — правильнее держать кеш и «важные» данные в разных экземплярах Redis, или хотя бы следить, чтобы память под кеш не кончалась.

→
ГЛАВНАЯ МЕТРИКА КЕША

Hit ratio = hits / (hits + misses). Если 95% — кеш работает отлично. Если 20% — он почти бесполезен: ключи слишком быстро истекают, сбрасываются слишком часто или кешируется не то. В продакшене эти цифры собирают Prometheus (через redis_exporter) и показывают в Grafana. Откройте MONITOR во втором терминале и подёргайте наши эндпоинты — группа увидит каждый GET, SET, INCR и EXISTS, который делает API.

i

А данные переживут перезапуск? Зависит от настроек: RDB — снимок памяти на диск раз в N минут; AOF — журнал всех команд. Для кеша это не важно (пустой кеш просто заново заполнится), для чёрного списка — желательно. В Docker-образе по умолчанию включены периодические снимки RDB.
